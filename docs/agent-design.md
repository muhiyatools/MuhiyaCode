# Agent and token-efficiency design

MuhiyaCode treats model turns—not individual tool bytes—as the dominant cost because the conversation prefix is resent on every request.

## Prompt compiler

- The full prompt is stable across turns and held below a regression ceiling of roughly 1,900 estimated tokens.
- Conversational and toolful tasks share one stable full prompt and pinned tool surface; task-specific policy stays in the user-message brief.
- Workspace, shell, model profile, and feature availability are session-stable substitutions. The current date rides in the task brief.
- Delegation guidance (feature 008) is a dedicated static `DELEGATION` section: positive criteria (delegate independent exploration of unread scope, parallelizable sub-parts, a review pass at high allowance), negative criteria (never single-thread work or already-read scope), and the brief semantics (`agents<=N` is the task's allowance to plan with). The `run_subagent` tool description carries when-to-use guidance with a worked example — the strongest inducement surface. Edit discipline rides the same epoch: surgical `edit_file`/`multi_edit` on existing files; `write_file` only for new files or explicit regeneration. One recorded upgrade epoch; byte-stable thereafter (baseline re-recorded in `prompt_budget_test.go`).
- Task class and budgets live in a compact final user-message brief, preserving the system prefix for provider caching.
- Provider family addenda are short and target known tool-call failure modes; leaked DSML or a single JSON call can be rescued without accepting unknown tool names.
- Workspace-resident skills (`.agents/skills`, `.codex/skills`) are advertised as a deterministic `SKILLS` section appended to the stable prompt: one `- name (workspace-relative path): description` line per skill, sorted by lowercased name, discovered once per session. Identical configuration yields byte-identical bytes, so the section never invalidates the prefix within a session. The model loads a skill's full instructions on demand via `read_file`; skill bodies never enter the prompt. External-root skills are excluded from the advertised listing (they stay reachable through the manual `/skills` flow) so on-demand reads stay inside the workspace containment boundary.

## Runtime governor

Prompts are classified as chat, tiny, small, standard, large, or epic. The class and effort ceiling determine turns, approximate tool budget, subagent cap, reasoning tier, and verification expectation. Tool budgets are convergence signals rather than hard stops. A growing task can escalate once; the final landing turn disables tools so the model must return a factual result. There is deliberately NO cumulative token ceiling (removed in v1.0.1): loop safety comes from the repeated-failure terminator, the loop-guard nudges, and the per-effort turn budget. Near-miss edits (`oldString not found` / ambiguous, with no change applied) classify as tool failures (feature 008), so DeepSeek's edit-fumble loop trips those guards instead of retrying invisibly; partially-applied batches and idempotent skips stay successes. At max effort, a task that changed files and still has agent allowance receives a one-time `[review]` tail nudge (the consumed `AutoReview` profile flag) — since feature 011 the nudge first consults the deterministic review gate (`reviewgate.go`), so trivial changes skip with a visible `review: skip — <reason>` line while risk-area changes (auth/billing/concurrency/security-config/migration paths) always review; `Large` classification now requires two corroborating size signals instead of one.

An incomplete plan causes bounded continuation instead of a premature "continue?" question. Mid-task steering is inserted at the next safe model boundary and extends runway without restarting valid work.

## Harness-enforced orchestration pipeline

Task classification selects a deterministic execution path. Chat, tiny, and small requests stay on the byte-compatible direct path. Standard work uses a light plan-first path. Large and epic work enters the full `research → plan → approve → implement → validate → done` state machine; legal transitions and completion gates live in the harness rather than depending on model phrasing.

Full-pipeline research is split into independent scopes and completed before any mutation. Its bounded findings enter the knowledge sidecar and durable `plan.md` artifact. Planning is read-only and must produce exact `[F#]`-grounded targets, observable acceptance checks, dependency intent, verification commands, and risks. Approval always pauses—even in auto-accept and headless modes—and the persisted phase makes pending or interrupted work resumable. Approved implementation steps are grouped by dependency and delegated to isolated workers; successful reports advance only their assigned steps. A separate review worker must return an explicit `VERDICT: PASS` before the harness permits `done`; since feature 011 that dispatch is gated (`review_gating` setting: off/conservative/default), tier-labeled (focused/deep with a greenfield cap), and token-ceilinged with graceful partial-coverage wrap-up — explicit user review requests bypass gating entirely via the ungated `run_subagent("review")` path.

The legacy saved-plan executor is suppressed after a full pipeline has already implemented and validated the plan, preventing the main agent from repeating edits and checks. Cross-phase handoffs carry a structured role, bounded scope/context, deliverable, and output format; full reports remain in durable session records while only compact summaries return to the main conversation. `explore`, `plan`, and `review` workers can run allow-listed read-only shell checks (`go test`, `go vet`, Git inspection, and search commands), while the shared dispatch gate blocks arbitrary shell mutation.

Pipeline phase, role, model, degradation, and validation state are visible in the event stream and TUI. A failed phase is recorded as a bounded degradation with remaining work—it is never relabeled as successful completion.

## Context memory

- Structured assistant tool calls and their results are always kept paired.
- Completed older tasks fold large tool payloads while retaining their compact truth.
- Read signatures and stitched line ranges prevent unchanged re-reads only while the earlier result remains intact.
- File fingerprints revoke stale coverage after an external edit. Agent mutations invalidate one path when possible and searches globally; conservative read-only shell commands preserve coverage.
- Knowledge stores bounded file notes and subagent reports. Identical read-only delegations at the same edit epoch reuse the report with zero model calls.
- Automatic compaction asks the model for a fixed `GOAL/STATE/FILES/DECISIONS/COMMANDS/PENDING` summary and includes durable knowledge facts. A deterministic fallback remains available if summarization fails.

## Project memory (cross-session)

- **The store, not the repo.** Durable memory lives in a per-project store directory outside the workspace — `~/.muhiya/projects/<project-id>/memory/`, where `<project-id>` is `<sanitized-basename>-<sha256[:8]>` of the canonical workspace path (legible and collision-safe). It never pollutes a repo, and because `~/.muhiya` is a hard-blocked sensitive root, the model's file tools can never read it: memory is reached ONLY through the engine-mediated `save_memory` / `recall_memory` tools. An existing workspace `MEMORY.md` is **copied once** into the store on first load (copy-only — the original is never modified or deleted).
- **Index + topics, for token efficiency.** The store holds an always-loaded index (`MEMORY.md`: standing facts plus `- [topic] description` pointer lines) and on-demand topic files (`<topic>.md`). Only the index HEAD (first 200 lines / 24 KiB) is injected at session start, so the always-loaded cost stays small however much detail accumulates. `save_memory` appends a plain fact to the index, or — with a `topic` — files the entry into `<topic>.md` and leaves just a one-line pointer in the index. `recall_memory` reads one topic file on demand when the index's pointer is relevant, so the model fetches detail only when it needs it instead of carrying it every turn. Entries are deduplicated, size-bounded (~500 chars each; topic files capped at 32 KiB, rejected not truncated), secret-screened, and gated by the same mutation-approval flow as file edits; `recall_memory` is read-only and needs no approval. The transcript renders both as "Memory" rows.
- **Instructions: user + project.** Two instruction layers load with identical containment, UTF-8/size (≤32 KiB), and secret-screening rules: an optional user-level `~/.muhiya/MUHIYA.md` (applies to every project) and a per-repo `MUHIYA.md` (like `CLAUDE.md`). On first use MuhiyaCode writes a clear per-repo `MUHIYA.md` template (never overwriting an existing file); the user edits it by hand. MuhiyaCode composes the user instructions, project instructions, and memory index into one byte-stable `## PROJECT CONTEXT` boot block (project instructions win on conflict) that rides the first user message. The block is composed once, persisted as the session's `RenderedBootContext`, and reused verbatim on resume, so it never recomputes mid-session and never disturbs the prefix cache; a pristine (comment-only) file reads as empty and costs zero prefix tokens.
- A mid-session change to the memory index or the project instructions — the agent's own `save_memory` / edit, or a manual user edit — surfaces exactly once as a one-shot `<memory-update>` / `<project-instructions-update>` tail on the next user message, gated on the file's content hash, then folds into the next session's cached prefix at no per-turn cost. None of this changes tools, model routing, or the deterministic prompt guarantees.

## Subagents

`explore`, `plan`, and `review` receive read-only registries. `general` receives the full tool registry for isolated implementation. Runs have independent contexts, lower reasoning tiers, strict turn limits, optional provider-reported token ceilings (feature 011: breach triggers one wrap-up turn and a `partial` label, never silent truncation), and shared durable knowledge. Each kind rides its own provider cache pin (`:sub:<kind>`), so sequential different-kind runs no longer evict each other's prefix caches; per-(model, pin) steady-state hit rates surface in `/context`, `TaskStats`, and the benchmark records. Multiple independent subagent calls execute in parallel only at effort levels that permit it; ordinary tools remain ordered. Each delegated mission carries an explicit capability statement — its exact, sorted toolset, the boundary that nothing else is available, and a report contract to flag ambiguity or architectural choices back to the caller rather than deciding them (tuned to DeepSeek's mechanical-worker strengths). For the launch configuration, routing `general` workers to `deepseek-v4-flash` via `SubagentModelID` while the orchestrator holds `deepseek-v4-pro` is the recommended posture.

The delegation budget is the smaller of the effort ceiling and the task-class cap; every effort tier (including `low`) grants at least one run for classes that support delegation. Because plan mode advertises `explore`/`plan`/`review` delegation in its brief, a plan-mode task guarantees a floor of one run so the advertised capability can never contradict a zero budget. When a real budget is exhausted mid-task, each report states the remaining count and denials escalate from a redirect ("work directly") to a hard stop; when the task has no budget at all (`agents=0`), the very first call is hard-closed, so a task converges on direct work instead of retrying a closed door.

## Plan lifecycle

An approved plan moves through an explicit phase machine — drafting, ready, pending, executing, then finished, interrupted, superseded, or discarded — persisted in the `plan_state.json` sidecar (additive `phase` field; legacy sidecars derive it from the older booleans on load). An executable hint ("say 'proceed'") appears only while a plan is genuinely pending; the moment execution begins — detected by the user's go-ahead or, phrasing-independently, by the first plan step that starts — the hint is withdrawn, and finishing all steps marks the plan finished so it never re-advertises as executable, even across resume. A run that ends with steps still open records the plan interrupted (resumable). When the model finalizes an executing plan with steps still open, the answer carries a harness-attributed disclosure of the incomplete steps so it never implies work it did not do.

### Plan vs to-dos

Two words, kept distinct in every surface. The **plan** is the *proposal*: what plan mode produces, what the approval modal gates, what `plan.md` stores — defined once and approved. The **to-dos** are the *live execution checklist*: the same steps with `pending` / `in_progress` / `completed` status that the agent ticks off as it works and the user watches under the input box (the `update_plan` tool name stays; only the surfaced wording changed). Rule of thumb: before execution it is the plan; once steps are being ticked it is the to-dos. So `update_plan`'s result reads "To-dos updated: N/M done", the completion audit discloses "N of M to-dos incomplete", and the old "Plan updated:" phrasing is forbidden by the offline gauntlet.

## Regression gates

Tests enforce prompt-size ceilings, stable prompt bytes, lite-tool isolation, history folding/intactness, range coverage and migration fixtures, effort/class budgets, bounded outputs, subagent limits/reuse, steering, final landing, and real streamed integration turns.
