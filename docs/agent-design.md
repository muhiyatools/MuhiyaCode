# Agent and token-efficiency design

MuhiyaCode treats model turns—not individual tool bytes—as the dominant cost because the conversation prefix is resent on every request.

## Prompt compiler

- The full prompt is stable across turns and held below a regression ceiling of roughly 1,900 estimated tokens.
- Conversational and toolful tasks share one stable full prompt and pinned tool surface; task-specific policy stays in the user-message brief.
- Workspace, shell, model profile, and feature availability are session-stable substitutions. The current date rides in the task brief.
- The static `DELEGATION` section is gone with the tool it taught. `OPERATING CONTRACT` now says so directly — rule 2 is *"you do the work yourself, in this session: investigate, change the files, run the checks. There is no one to hand work to."* `CONTEXT AND EDIT DISCIPLINE` folds what used to be split across two system prompts back into one: the main loop's reading rules and the executor's editing rules — surgical `edit_file`/`multi_edit` on existing files, `write_file` only for new files or explicit regeneration — are taught once, to the one model that both reads and edits, instead of half of it going to a model that was forbidden from acting on it. A short new `MODEL` section replaces `DELEGATION`'s slot: the active model can now change between tasks, so it tells the model never to narrate or request a switch and to treat every earlier turn as its own regardless of which model produced it.
- The unified-session epoch recorded another cache epoch: the system prompt grew 708 characters (to 6,101, against a 6,120 regression ceiling) as `CONTEXT AND EDIT DISCIPLINE` absorbed the executor's former text and picked up `MODEL`. But the fixed prefix it rides beside — prompt plus tool JSON — fell from 24,393 to 21,908 bytes (-10.2%): deleting `run_subagent`'s schema (its description plus the task/role/skills property texts) cut the tool JSON by 3,214 bytes, more than paying for the prompt's growth. A session resumed across the upgrade pays exactly one attributed cold start, then the new prefix is byte-stable (baseline recorded in `prompt_budget_test.go`).
- Planning is a compact static `PLANNING` section, not a mode or a tool (see *Planning as an internal skill*). It lives in the cached prefix rather than a loadable skill file because the skill store sits under `~/.muhiya`, which the model's file tools cannot read, and because a cached short section costs nothing per turn while a lazily loaded one costs a round trip every time.
- The workspace checklist (`tasks.md`) is deliberately NOT in the prefix. It changes on almost every turn, so injecting it would invalidate the cache continuously; the model reads it on demand like any other file.
- v1.1.0 recorded one cache epoch: the system prompt moved 5,777 → 5,246 characters and the tool JSON 20,317 → 18,578 bytes. Removing the pipeline paid for the planning, checklist, role-split, and trust-the-report text with room to spare. A session resumed across the upgrade pays exactly one attributed cold start.
- Task class and its turn/tool budgets live in a compact final user-message brief, preserving the system prefix for provider caching.
- Every frontend assembles the user message through one function, `app.AssemblePrompt`, so the TUI, line mode, and one-shot mode send identical prompt bytes for identical input. They previously diverged on Unicode normalization, queued-skill text, and paste expansion, which meant the same typed request could produce different bytes — and a different cache outcome — depending on how it was entered.
- Provider family addenda are short and target known tool-call failure modes; leaked DSML or a single JSON call can be rescued without accepting unknown tool names.
- Skills from **every** root (`<workspace>/.agents/skills`, `<workspace>/.codex/skills`, `$MUHIYA_SKILLS_DIR`, `~/.codex/skills`, `~/.agents/skills`, first-wins on duplicate names) are advertised as a deterministic `SKILLS` section appended to the stable prompt: one `- name: description` line per skill, sorted by lowercased name, discovered once per session and frozen for its lifetime. Identical configuration yields byte-identical bytes, so the section never invalidates the prefix within a session. Skill bodies never enter the prompt — the model loads one on demand through `read_skill`, and the body arrives as an ordinary tool result in the append-only tail.
- `read_skill` is name-keyed rather than path-keyed, which is what makes home-root skills reachable without widening file-tool containment: the tool takes no path and can serve only the `SKILL.md` files this session already catalogued (`docs/security.md`). Bodies are bounded at 32 KiB. The engine tracks a per-task provided-set, seeded from any `<skill name="…">` blocks the manual `/skills` flow already wrapped into the prompt, so a skill is never transmitted twice in one task.
- Selection is the model's judgment, not a harness keyword match: the prefix hint tells it to read a relevant skill *before* starting the related work and keep applying it for the rest of the task, blending the guidance with its own reasoning rather than reciting it.

## Runtime governor

Prompts are classified as chat, tiny, small, standard, large, or epic. Since v1.1.0 the classifier only *sizes* work — it no longer selects an execution path, and there is no `NeedsPlan` verdict or pipeline depth. Size determines turns, approximate tool budget, reasoning tier, and verification expectation; the model decides how to approach the task. (A request to *create* a plan, or one pointing at a plan document, is still floored at `small` so it is never treated as chat — the classifier sizes the planning request, it does not route it.) Tool budgets are convergence signals rather than hard stops. A growing task climbs a **runway ladder**: whenever it reaches its cap while files are still changing it escalates a class and earns more turns, repeatedly, up to `epic` and the effort-scaled `hardTurnCeiling`. The final landing turn disables tools so the model must return a factual result. There is deliberately NO cumulative token ceiling (removed in v1.0.1): loop safety comes from the repeated-failure terminator, the loop-guard nudges, and the per-effort turn budget. Near-miss edits (`oldString not found` / ambiguous, with no change applied) classify as tool failures (feature 008), so DeepSeek's edit-fumble loop trips those guards instead of retrying invisibly; partially-applied batches and idempotent skips stay successes. At max effort, a task that changed at least two files receives a one-time `[review]` tail nudge (the consumed `AutoReview` profile flag) — since feature 011 the nudge first consults the deterministic review gate (`reviewgate.go`), so trivial changes skip with a visible `review: skip — <reason>` line while risk-area changes (auth/billing/concurrency/security-config/migration paths) always review; `Large` classification now requires two corroborating size signals instead of one.

An unfinished checklist causes bounded continuation instead of a premature "continue?" question. Mid-task steering is inserted at the next safe model boundary and extends runway without restarting valid work, so a message typed during a long build does not wait minutes for the loop to resume.

A failed provider request no longer kills the task. A stream that dies after headers is retried once by the provider (identical bytes against a just-cached prefix, so it pays cache-hit rates), and the main loop gets one further recovery attempt before giving up. Retries are gated by `gateway.Recoverable`: transport failures and 5xx yes, a bad key or an exhausted budget never — those repeat identically, and the user is told what to fix. On a 429 the harness consults `/v1/usage` to distinguish throttling (wait) from a spent budget (stop), because the gateway answers both with the same status.

## One unified session

v1.1.0 removed the orchestration pipeline entirely. There is no `research → plan → approve → implement → validate → done` state machine, no 11-state lifecycle, no approval modal, no plan mode, and no `update_plan` / `exit_plan_mode` / `read_plan` tools. In v1.1.0 what replaced the pipeline was still a division of labor: a main model that planned, analyzed, and instructed, with every workspace change delegated to an execution subagent (kind `general`) through `run_subagent`, backstopped by an `executionRoleGate` (`rolesplit.go`) that refused `edit_file`, `multi_edit`, `write_file`, `apply_patch`, mutating `run_shell`, and `mcp__*` calls from the main loop.

That division of labor is gone too. There is now exactly one model, and it follows instructions directly, the way Claude Code does: it reads, edits, runs shells, and verifies in the same session, with no gate distinguishing a "planning" call from an "executing" one.

The role gate earned its removal in the field, not on principle: a live session had the model generate a whole file, paying the tokens to produce it, and then the gate refused the write and told it to delegate instead — discarding a fully generated result over an internal boundary the user never asked for and could not see. A split that occasionally throws away paid-for work was not worth keeping.

**`OPERATING CONTRACT` states the new shape directly.** Rule 2: *"You do the work yourself, in this session: investigate, change the files, run the checks. There is no one to hand work to."* The full tool registry is always available — nothing is capability-gated by role, and no call is refused on the grounds that it belongs to a different agent. `CONTEXT AND EDIT DISCIPLINE` folds what used to be split across two system prompts — the main loop's reading rules and the executor's editing rules — into one section, because the model that reads a file is now the model that edits it.

What survives from the split: the deterministic review gate (`reviewgate.go`, feature 011, `reviewGating`: off/conservative/default) still decides whether a change is substantial or risky enough to warrant a dedicated review pass and how deep it should go, with a user-visible rationale line (`review: <tier> — <reason>`); risk-area changes (auth, billing, concurrency, security config, migrations) still always review regardless of size, and trivial changes still skip. What changed is who does the reviewing: there is no review subagent to dispatch, so a warranted review becomes one more thing the single session does for itself before it gives its final answer. A user who explicitly asks for a review always gets one, the same as any other explicit request — there is no separate gated path to bypass.

Degradation and verification state are still visible in the event stream and TUI. A task that hits its liveness limits before finishing is recorded as a bounded degradation with remaining work — it is never relabeled as successful completion.

## Verification is direct

The plan/execute split's payoff depended on the planner not redoing the executor's work, and it did not: the reason was a contradiction between two instruction surfaces, the operating contract's "verify to the brief" against `DELEGATION`'s "treat its report as ground truth." A field test showed how the model resolved it — by re-reading every file the executor had just verified, on the expensive main stream, after the check had already passed. That contradiction needed a whole protocol to fix: a machine-readable `STATUS: COMPLETE` / `NEEDS-VERIFY` / `BLOCKED` line on every executor report, a parser for it, and a contract rule telling the main model to trust a report that showed its checks instead of re-running them itself. That parser is gone along with the reports it read; `orchestrator/checklist.go` now holds only the `tasks.md` checklist logic described below.

With one model doing both the change and the check, the contradiction has nowhere left to live, and neither does the protocol that resolved it — there is no second party's report to trust or distrust. `OPERATING CONTRACT` states verification as a single rule instead: rule 5, *"Verify what you change: after a change, run the check that proves it works, then tick its item. Never report a result you did not observe."* Rule 6 closes the loop — *"Wrap up flat: when every item is checked and its check passed, answer and stop. Do not re-read files you have already read, re-run checks that already passed, or add a validation pass the work did not need."* `CACHE DISCIPLINE` reinforces it from the caching side: every past read, search, and diff already in the conversation is current truth, so redoing any of it is cache waste by definition, not diligence.

## Planning as an internal skill

Planning is neither a mode nor a tool: it is a compact `PLANNING` section in the cached prefix, applied only when the work is genuinely large or the user asks for a plan outright. Small clear tasks are executed, not planned. The skill tells the model to recall project memory first (constraints, past decisions, similar plans), read the code it intends to change rather than plan against assumptions, write the plan into `tasks.md`, and save the durable decisions once the work settles.

**A plan is a file, and its items are executable.** Step 3 sets the standard: written into `tasks.md`, created in the directory the work targets — the workspace root only when the work spans the whole workspace (TA01; see *Workspace checklist* below) — each item names its files, its change, and its check, and must be runnable *without further design decisions*: put the thinking in the item, not in your head, plus a Notes section for constraints and risks. Step 4 makes the file the deliverable: if the user asked for a PLAN, write `tasks.md` **first**, then summarize it and stop; otherwise start executing it yourself, ticking each item as its check passes. Presenting a plan the model only holds in context is an instruction violation, not a style choice — a bare "Go" in the next turn needs a file to act against, not a chat message to reparse.

The memory clauses are the point of the bookends: planning starts by recalling what this project already decided and ends by recording what this plan decided, so the next session does not relitigate it.

## Workspace checklist (`tasks.md`)

For multi-step work the model keeps a plain markdown checklist, written with ordinary file tools — usually at the workspace root, or created in the directory the work targets when a task is scoped to one part of it. (TA01: this used to be hard-wired to the workspace root on the read side while writes were already accepted anywhere, so a checklist created beside the work — the natural place, and what the instructions now ask for — landed on disk and was never read again; the to-do panel stayed empty and the completion-honesty guard went blind.) There is no checklist tool and the harness never authors the file — it only observes. Any `- [ ] item` / `- [x] item` line is an item; an explicit `(in progress)` suffix overrides to in-progress. The optional status parenthetical is what the old `plan.md` parser *required*, which meant a plain checklist — exactly what the instructions teach the model to write — parsed to nothing.

The engine watches for writes to that path in the dispatch gate, re-parses the file on a hit, and pushes the result to the live to-do panel. One file is the single source of truth for the panel and for the completion-honesty guard: an answer that finalizes a task with items still open carries a harness-attributed disclosure of exactly which ones, so it never implies work it did not do.

## Context memory

- Structured assistant tool calls and their results are always kept paired.
- Completed older tasks fold large tool payloads while retaining their compact truth.
- Read signatures and stitched line ranges prevent unchanged re-reads only while the earlier result remains intact.
- File fingerprints revoke stale coverage after an external edit. Agent mutations invalidate one path when possible and searches globally; conservative read-only shell commands preserve coverage.
- Knowledge stores bounded, per-file notes — what a read found, or that a file was edited — as durable, low-cost facts about the workspace.
- Automatic compaction asks the model for a fixed `GOAL/STATE/FILES/DECISIONS/COMMANDS/PENDING` summary and includes durable knowledge facts. A deterministic fallback remains available if summarization fails.

## Project memory (cross-session)

- **The store, not the repo.** Durable memory lives in a per-project store directory outside the workspace — `~/.muhiya/projects/<project-id>/memory/`, where `<project-id>` is `<sanitized-basename>-<sha256[:8]>` of the canonical workspace path (legible and collision-safe). It never pollutes a repo, and because `~/.muhiya` is a hard-blocked sensitive root, the model's file tools can never read it: memory is reached ONLY through the engine-mediated `save_memory` / `recall_memory` tools. An existing workspace `MEMORY.md` is **copied once** into the store on first load (copy-only — the original is never modified or deleted).
- **Index + topics, for token efficiency.** The store holds an always-loaded index (`MEMORY.md`: standing facts plus `- [topic] description` pointer lines) and on-demand topic files (`<topic>.md`). Only the index HEAD (first 200 lines / 24 KiB) is injected at session start, so the always-loaded cost stays small however much detail accumulates. `save_memory` appends a plain fact to the index, or — with a `topic` — files the entry into `<topic>.md` and leaves just a one-line pointer in the index. `recall_memory` reads one topic file on demand when the index's pointer is relevant, so the model fetches detail only when it needs it instead of carrying it every turn. Entries are deduplicated, size-bounded (~500 chars each; topic files capped at 32 KiB, rejected not truncated), secret-screened, and gated by the same mutation-approval flow as file edits; `recall_memory` is read-only and needs no approval. The transcript renders both as "Memory" rows.
- **Instructions: user + project.** Two instruction layers load with identical containment, UTF-8/size (≤32 KiB), and secret-screening rules: an optional user-level `~/.muhiya/MUHIYA.md` (applies to every project) and a per-repo `MUHIYA.md` (like `CLAUDE.md`). On first use MuhiyaCode writes a clear per-repo `MUHIYA.md` template (never overwriting an existing file); the user edits it by hand. MuhiyaCode composes the user instructions, project instructions, and memory index into one byte-stable `## PROJECT CONTEXT` boot block (project instructions win on conflict) that rides the first user message. The block is composed once, persisted as the session's `RenderedBootContext`, and reused verbatim on resume, so it never recomputes mid-session and never disturbs the prefix cache; a pristine (comment-only) file reads as empty and costs zero prefix tokens.
- A mid-session change to the memory index or the project instructions — the agent's own `save_memory` / edit, or a manual user edit — surfaces exactly once as a one-shot `<memory-update>` / `<project-instructions-update>` tail on the next user message, gated on the file's content hash, then folds into the next session's cached prefix at no per-turn cost. None of this changes tools, model routing, or the deterministic prompt guarantees.

## The model and the task advisor

The user never manages models. `/model` is gone, and so is every model name in the TUI chrome. There is one role now, not three: a single active model does the whole task — planning, editing, verifying — plus a **utility model** resolved on the fly for cheap auxiliary calls (the advisor's own call, onboarding). The utility model is never a persisted setting: it is whichever catalog entry's id or name contains "flash", or failing that the smallest-window entry, or failing that the active model itself, so a catalog without a Flash-class entry still works instead of failing.

**The model is frozen for a task, not a session.** A **task advisor** runs at the start of *every* task, not just the session's first — because that is the only moment a switch is safe: no request for this task has gone out yet. It is a small utility-model call (200 max tokens, 8-second timeout, its own `:sub:advisor` pin) that sees the current model, the catalog with each model's window/family/continuation support, how many tokens a cold start on an unseen model would cost right now, which models are already warm this session, a one-line workspace size signal, and the prompt. Its expected answer is `keep`; it exists for the task that obviously outgrows the current model.

Two hard gates sit below the advisor's judgment and it cannot argue past either:

- **FIT** — the conversation this task inherits must fit the candidate's context window with headroom (roughly 30% for growth, plus the model's own output budget), or the assembler would silently drop the oldest messages to make it fit.
- **COST** — provider prefix caches are per-model, so a model this session has never sent the conversation to re-reads all of it as uncached input on its first request. That is affordable while the conversation is under `coldStartCapTokens` (25,000 tokens) — generous headroom for a session's early tasks — and affordable at any size when returning to a model already **warm** in this session. Otherwise the switch would cost more than it can plausibly win, and the current model — whose cache is already warm — keeps the task.

Warmth is tracked in `Engine.warmPrefix`, a map from model id to the history revision it last saw a conversation at, updated only when a **main-stream** request completes — the advisor's own call and other auxiliary traffic never count, or the advisor would end up recommending a switch to the one model guaranteed to cold-start. A compaction, a pressure trim, or a completed-task fold rewrites earlier messages in place, so every model's recorded warmth retires along with the revision it described; a resumed session starts with an empty warm ledger and treats every model as cold, which is the conservative direction for a resume. `warmModelsThisSession` lists the still-warm models, most-recently-used first, and both the advisor's prompt (under a `SWITCH COST` heading) and the `/context` card's "Warm:" row read from it.

Every advisor failure mode — disabled, pinned, empty catalog, timeout, malformed answer, an unknown model id, a FIT or COST decline, an apply error — silently keeps the current model. The advisor must never be a point of failure; a task that runs is worth more than a marginally better model.

Mid-session, genuinely different large work that shares nothing with what the session has already done does not switch anything either — that is a separate, one-time advisory: *"/new would give it a clean start and a fresh cache"*, costing no model call and blocking nothing. The model choice and the conversation's cache are different problems; a fresh model bolted onto a conversation still full of unrelated history saves nothing.

Escape hatches: `muhiyacode config set model <id>` pins the model (pinning disables the advisor outright), and `config set advisor off` disables it directly without pinning anything. A 24-hour TTL refresh keeps the gateway model catalog current so the advisor and the utility-model resolution work against real entries.

## Regression gates

Tests enforce prompt-size ceilings, stable prompt bytes, lite-tool isolation, history folding/intactness, range coverage and migration fixtures, effort/class budgets, bounded outputs, steering, final landing, and real streamed integration turns. Checklist parsing and the completion disclosure are covered in `checklist_test.go` and `completion_audit_test.go`. The task advisor's per-task firing, its FIT/COST gates, and its silent failure modes are covered in `advisor_test.go` and `switchcost_test.go`. `internal/instructions/audit_test.go` asserts that no registered prompt text names `run_subagent` — a tool that no longer exists — so a stray leftover mention can never advertise a capability the model can no longer call.
