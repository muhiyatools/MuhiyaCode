# Agent and token-efficiency design

MuhiyaCode treats model turns—not individual tool bytes—as the dominant cost because the conversation prefix is resent on every request.

## Prompt compiler

- The full prompt is stable across turns and held below a regression ceiling of roughly 1,900 estimated tokens.
- Conversational and toolful tasks share one stable full prompt and pinned tool surface; task-specific policy stays in the user-message brief.
- Workspace, shell, model profile, and feature availability are session-stable substitutions. The current date rides in the task brief.
- Delegation guidance is a dedicated static `DELEGATION` section, rewritten in v1.1.0 around the plan/execute split: `general` executes every workspace change and each follow-up chains to it for a warm context; `explore` earns a run only for broad reading of code not already in context; `review` for an independent verdict after substantial edits; one agent at a time; each run gets one deliverable and can neither see the conversation nor ask a question. There is no run limit and no allowance in the brief — the section teaches the judgment instead: *match the dispatch to the work, so a one-line fix is ONE short run, never a survey*. The `run_subagent` tool description carries when-to-use guidance with a worked example — the strongest inducement surface — and its `task` property states the handoff standard: the goal, the exact files and symbols, the specific change in each, the constraints it must not break, and the exact command that proves it worked, because the executor runs on a cheaper model and *any design decision you leave out is one it will make for you*. Edit discipline rides the same epoch: surgical `edit_file`/`multi_edit` on existing files; `write_file` only for new files or explicit regeneration. One recorded upgrade epoch; byte-stable thereafter (baseline re-recorded in `prompt_budget_test.go`).
- Planning is a compact static `PLANNING` section, not a mode or a tool (see *Planning as an internal skill*). It lives in the cached prefix rather than a loadable skill file because the skill store sits under `~/.muhiya`, which the model's file tools cannot read, and because a cached short section costs nothing per turn while a lazily loaded one costs a round trip every time.
- The workspace checklist (`tasks.md`) is deliberately NOT in the prefix. It changes on almost every turn, so injecting it would invalidate the cache continuously; the model reads it on demand like any other file.
- v1.1.0 recorded one cache epoch: the system prompt moved 5,777 → 5,246 characters and the tool JSON 20,317 → 18,578 bytes. Removing the pipeline paid for the planning, checklist, role-split, and trust-the-report text with room to spare. A session resumed across the upgrade pays exactly one attributed cold start.
- Task class and its turn/tool budgets live in a compact final user-message brief, preserving the system prefix for provider caching. The brief carries no agent count: delegation scale is a judgment, not a number to spend down.
- Every frontend assembles the user message through one function, `app.AssemblePrompt`, so the TUI, line mode, and one-shot mode send identical prompt bytes for identical input. They previously diverged on Unicode normalization, queued-skill text, and paste expansion, which meant the same typed request could produce different bytes — and a different cache outcome — depending on how it was entered.
- Provider family addenda are short and target known tool-call failure modes; leaked DSML or a single JSON call can be rescued without accepting unknown tool names.
- Workspace-resident skills (`.agents/skills`, `.codex/skills`) are advertised as a deterministic `SKILLS` section appended to the stable prompt: one `- name (workspace-relative path): description` line per skill, sorted by lowercased name, discovered once per session. Identical configuration yields byte-identical bytes, so the section never invalidates the prefix within a session. The model loads a skill's full instructions on demand via `read_file`; skill bodies never enter the prompt. External-root skills are excluded from the advertised listing (they stay reachable through the manual `/skills` flow) so on-demand reads stay inside the workspace containment boundary.

## Runtime governor

Prompts are classified as chat, tiny, small, standard, large, or epic. Since v1.1.0 the classifier only *sizes* work — it no longer selects an execution path, and there is no `NeedsPlan` verdict or pipeline depth. Size determines turns, approximate tool budget, reasoning tier, and verification expectation — never a subagent count; the model decides how to approach the task. (A request to *create* a plan, or one pointing at a plan document, is still floored at `small` so it is never treated as chat — the classifier sizes the planning request, it does not route it.) Tool budgets are convergence signals rather than hard stops. A growing task climbs a **runway ladder**: whenever it reaches its cap while files are still changing it escalates a class and earns more turns, repeatedly, up to `epic` and the effort-scaled `hardTurnCeiling`. The files it counts include the execution agent's — under the plan/execute split the main model writes nothing but `tasks.md`, so a main-loop-only tally read every delegated task as "changed nothing" and refused to extend. The final landing turn disables tools so the model must return a factual result. There is deliberately NO cumulative token ceiling (removed in v1.0.1): loop safety comes from the repeated-failure terminator, the loop-guard nudges, and the per-effort turn budget. Near-miss edits (`oldString not found` / ambiguous, with no change applied) classify as tool failures (feature 008), so DeepSeek's edit-fumble loop trips those guards instead of retrying invisibly; partially-applied batches and idempotent skips stay successes. At max effort, a task that changed at least two files receives a one-time `[review]` tail nudge (the consumed `AutoReview` profile flag) — since feature 011 the nudge first consults the deterministic review gate (`reviewgate.go`), so trivial changes skip with a visible `review: skip — <reason>` line while risk-area changes (auth/billing/concurrency/security-config/migration paths) always review; `Large` classification now requires two corroborating size signals instead of one.

An unfinished checklist causes bounded continuation instead of a premature "continue?" question. Mid-task steering is inserted at the next safe model boundary and extends runway without restarting valid work — including into a subagent that is *already running*, which folds it into the current run as a course correction and notifies the parent, so a message typed during a long build no longer waits minutes for the main loop to resume.

A failed provider request no longer kills the task. A stream that dies after headers is retried once by the provider (identical bytes against a just-cached prefix, so it pays cache-hit rates), and the main loop and each subagent run get one further recovery attempt before giving up. Retries are gated by `gateway.Recoverable`: transport failures and 5xx yes, a bad key or an exhausted budget never — those repeat identically, and the user is told what to fix. On a 429 the harness consults `/v1/usage` to distinguish throttling (wait) from a spent budget (stop), because the gateway answers both with the same status.

## Plan/execute role split

v1.1.0 removed the orchestration pipeline entirely. There is no `research → plan → approve → implement → validate → done` state machine, no 11-state lifecycle, no approval modal, no plan mode, and no `update_plan` / `exit_plan_mode` / `read_plan` tools. The agent follows instructions directly, the way Claude Code does. What replaced the pipeline is a division of labor, not a sequence of phases.

**The main model plans, analyzes, and instructs; it does not execute.** Every workspace change is delegated to an execution subagent (kind `general`) through `run_subagent`. Two layers enforce this. The instruction layer — the operating contract and the `run_subagent` description — teaches the model to compose a handoff and delegate. The `executionRoleGate` (`rolesplit.go`) is the second layer, so a model that forgets gets a specific, actionable refusal instead of quietly doing the executor's job in the expensive stream. It refuses `edit_file`, `multi_edit`, `write_file`, `apply_patch`, any non-read-only `run_shell`, and any `mcp__*` call (an MCP tool can write files, so it counts as execution; unparseable shell arguments fail closed to "mutating").

Four carve-outs, each with a reason:

- **`tasks.md`** — the checklist is the execution strategy, and writing it is planning work.
- **Read-only shell** — builds, tests, and status probes are how the planner verifies a report; blocking them would leave it unable to check the executor's work.
- **`save_memory` / `edit_memory`** — recording decisions is planning, and the memory store is not the workspace.
- **Subagent scopes** — the gate keys on the main loop only, so the executor can obviously execute.

The gate escalates rather than repeating: after three blocks in a task the message changes, because a gate that returns the same sentence forever is indistinguishable from a loop. It never records into the failed-call cache — the identical call is legitimate the moment the executor makes it, and a cached denial would poison the executor's own attempt.

**There are no subagent budgets.** Per-class allowances existed briefly (`0/1/1/2/5/8`) and were deleted after the first owner field test showed that a quota and the role split are jointly incoherent. The transcript: a plan was presented, the user typed "Go", the classifier sized that turn as `chat`, the brief said `agents=0`, and the split forbids main-loop edits — so the agent had **no legal action at all** and asked the user to send another message. Raising the numbers would only move the corner; the fix was to stop counting. Gone with the map: `Budget.MaxAgentRuns`, the engine's per-task cap and denial counter, the denial gate in `runSubagentInput`, the escalating budget-denial texts, the "N subagent run(s) remaining" note appended to every report, and the `agents<=N` field in the task brief.

Delegation scale is now the model's judgment, taught rather than enforced. What still bounds a task is unchanged and deliberately not a budget: one agent at a time, the plan/execute split itself, and every liveness guard — the hard turn ceiling, the H5 distinct-failure terminator, the repeat limiter, the B7 all-failed detector, and each run's own `MaxTurns` with its INV-3 wrap-up. Those stop loops, not work. The regression lives in `subagent_dispatch_test.go` and `fieldtest_e2e_test.go`: a `chat`-classified continuation can dispatch.

Dispatch remains **model-driven**: the harness never launches subagents on its own. The review gate (`reviewgate.go`, `review_gating`: off/conservative/default) still decides skip/focused/deep and composes the exact review task, but the model launches the review subagent; explicit user review requests always run ungated. Handoffs carry a structured role, bounded scope/context, deliverable, and output format; full reports remain in durable session records while only compact summaries return to the main conversation. `explore` and `review` workers can run allow-listed read-only shell checks (`go test`, `go vet`, Git inspection, and search commands), while the shared dispatch gate blocks arbitrary shell mutation.

Role blocks, delegation, model, degradation, and verification state are visible in the event stream and TUI. A failed run is recorded as a bounded degradation with remaining work — it is never relabeled as successful completion.

## Verification is pull, not push

The role split only pays off if the planner stops redoing the executor's work. It did not, and the reason was a contradiction between two instruction surfaces: the operating contract's rule 6 said "Verify to the brief: run the checks yourself" while `DELEGATION` said "treat its report as ground truth". The field test showed how the model resolved it — by re-reading every file the agent had just verified, on the expensive main stream, after the check had already passed.

The contract now pulls instead of pushing. Rule 5 is *trust the report*: a report showing its checks and their results is final — the main model never re-reads its files or re-runs its checks. Re-verification happens only when the report **asks** for it (`NEEDS-VERIFY` or `BLOCKED`) or shows no verification at all, and then the model runs exactly the named check, not a sweep. Rule 6 closes the loop: wrap up flat — accept the report, tick `tasks.md`, answer; no second pass. `CACHE DISCIPLINE` names agent reports alongside past reads, searches, and edit diffs as current truth, so "re-check what a report verified" is cache waste by definition. The old rule 5 (one agent at a time, chain follow-ups) was deleted as a duplicate of `DELEGATION`, which paid for part of the new text.

Trust has to be earned on the other side, so the executor's report format ends in a machine-readable claim:

> Changes made with file:line; Verification: each check you ran and its result; Problems; Remaining concerns; then a final line — `STATUS: COMPLETE`, or `STATUS: NEEDS-VERIFY: <the exact command the caller should run>`, or `STATUS: BLOCKED: <what stopped you>`.

`SubagentGeneralSystem` tells the executor *why*: its caller trusts the report instead of re-checking, so `COMPLETE` is claimable only when the check actually ran and passed. `parseReportStatus` (`orchestrator/checklist.go`) parses that line — last `STATUS` line wins, spacing and case lenient because the executor is a cheaper model, and a **missing** status parses as `UNKNOWN`, never `COMPLETE`, because silence is not a claim. The parsed value rides the `run_summary` event as `reportStatus`. That is observability only: nothing in the harness branches on it, and launching stays the model's decision — the point is that a model which keeps omitting its status is visible in telemetry rather than quietly trusted.

## Planning as an internal skill

Planning is neither a mode nor a tool: it is a compact `PLANNING` section in the cached prefix, applied only when the work is genuinely large or the user asks for a plan outright. Small clear tasks are executed, not planned. The skill tells the model to recall project memory first (constraints, past decisions, similar plans), read the code it intends to change rather than plan against assumptions, write the plan into `tasks.md`, and save the durable decisions once the work settles.

**A plan is a file, and its items are executable.** Step 3 sets the standard: each item names its files, its change, and its check, and must be runnable by the execution agent *without further design decisions* — put the thinking in the item, not in your head — plus a Notes section for constraints and risks. That standard is the whole payoff of the plan/execute split: the executor is a cheaper model that cannot see the conversation and cannot ask a question, so an under-specified item is not saved effort, it is a decision deferred to the worst-placed party and paid for in executor turns. Step 4 makes the file the deliverable: if the user asked for a PLAN, write `tasks.md` **first**, then summarize it and stop. Presenting a plan the model only holds in context is an instruction violation, not a style choice — the field test's "Go" turn had nothing durable to execute against.

The memory clauses are the point of the bookends: planning starts by recalling what this project already decided and ends by recording what this plan decided, so the next session does not relitigate it.

## Workspace checklist (`tasks.md`)

For multi-step work the model keeps a plain markdown checklist at the workspace root, written with ordinary file tools. There is no checklist tool and the harness never authors the file — it only observes. Any `- [ ] item` / `- [x] item` line is an item; an explicit `(in progress)` suffix overrides to in-progress. The optional status parenthetical is what the old `plan.md` parser *required*, which meant a plain checklist — exactly what the instructions teach the model to write — parsed to nothing.

The engine watches for writes to that path in the **shared** dispatch gate, so a checklist edit counts whether the main loop or the execution subagent made it, then re-parses the file and pushes the result to the live to-do panel. One file is the single source of truth for the panel and for the completion-honesty guard: an answer that finalizes a task with items still open carries a harness-attributed disclosure of exactly which ones, so it never implies work it did not do.

## Context memory

- Structured assistant tool calls and their results are always kept paired.
- Completed older tasks fold large tool payloads while retaining their compact truth.
- Read signatures and stitched line ranges prevent unchanged re-reads only while the earlier result remains intact.
- File fingerprints revoke stale coverage after an external edit. Agent mutations invalidate one path when possible and searches globally; conservative read-only shell commands preserve coverage.
- Knowledge stores bounded file notes and subagent reports. Identical read-only delegations at the same edit epoch reuse the report with zero model calls.
- Automatic compaction asks the model for a fixed `GOAL/STATE/FILES/DECISIONS/COMMANDS/PENDING` summary and includes durable knowledge facts. A deterministic fallback remains available if summarization fails.

## Project memory (cross-session)

- **The store, not the repo.** Durable memory lives in a per-project store directory outside the workspace — `~/.muhiya/projects/<project-id>/memory/`, where `<project-id>` is `<sanitized-basename>-<sha256[:8]>` of the canonical workspace path (legible and collision-safe). It never pollutes a repo, and because `~/.muhiya` is a hard-blocked sensitive root, the model's file tools can never read it: memory is reached ONLY through the engine-mediated `save_memory` / `recall_memory` tools. An existing workspace `MEMORY.md` is **copied once** into the store on first load (copy-only — the original is never modified or deleted).
- **Index + topics, for token efficiency.** The store holds an always-loaded index (`MEMORY.md`: standing facts plus `- [topic] description` pointer lines) and on-demand topic files (`<topic>.md`). Only the index HEAD (first 200 lines / 24 KiB) is injected at session start, so the always-loaded cost stays small however much detail accumulates. `save_memory` appends a plain fact to the index, or — with a `topic` — files the entry into `<topic>.md` and leaves just a one-line pointer in the index. `recall_memory` reads one topic file on demand when the index's pointer is relevant, so the model fetches detail only when it needs it instead of carrying it every turn. Entries are deduplicated, size-bounded (~500 chars each; topic files capped at 32 KiB, rejected not truncated), secret-screened, and gated by the same mutation-approval flow as file edits; `recall_memory` is read-only and needs no approval. The transcript renders both as "Memory" rows.
- **Instructions: user + project.** Two instruction layers load with identical containment, UTF-8/size (≤32 KiB), and secret-screening rules: an optional user-level `~/.muhiya/MUHIYA.md` (applies to every project) and a per-repo `MUHIYA.md` (like `CLAUDE.md`). On first use MuhiyaCode writes a clear per-repo `MUHIYA.md` template (never overwriting an existing file); the user edits it by hand. MuhiyaCode composes the user instructions, project instructions, and memory index into one byte-stable `## PROJECT CONTEXT` boot block (project instructions win on conflict) that rides the first user message. The block is composed once, persisted as the session's `RenderedBootContext`, and reused verbatim on resume, so it never recomputes mid-session and never disturbs the prefix cache; a pristine (comment-only) file reads as empty and costs zero prefix tokens.
- A mid-session change to the memory index or the project instructions — the agent's own `save_memory` / edit, or a manual user edit — surfaces exactly once as a one-shot `<memory-update>` / `<project-instructions-update>` tail on the next user message, gated on the file's content hash, then folds into the next session's cached prefix at no per-turn cost. None of this changes tools, model routing, or the deterministic prompt guarantees.

## Subagents

There are three capability classes: `explore` and `review` receive read-only registries; `general` receives the full tool registry and is the only thing that changes the workspace. (The `plan` kind is gone with the pipeline.) Runs have independent contexts, lower reasoning tiers, and shared durable knowledge. Since v1.1.0 a run ends on **physics, not budget**: the per-kind `MaxTurns` is a ladder rung that a run still opening new files keeps earning (a run whose touched-set stops growing has stopped working, and that is what wraps it up), and the real bound is context-window pressure — at 85% of the model's window the run wraps up gracefully and is labeled `partial (context window)` so the caller dispatches a continuation, instead of dying on a provider context-length error with no report at all. The old `TokenCeiling` is gone; it was a budget, and it was never set outside its own test. `subagentHardCeiling` remains only as a liveness backstop for a provider that reports no usage. Each kind rides its own provider cache pin (`:sub:<kind>`), so sequential different-kind runs no longer evict each other's prefix caches; per-(model, pin) steady-state hit rates surface in `/context`, `TaskStats`, and the benchmark records. Subagent calls always execute one at a time — feature 014 removed the parallel-agents effort flag outright — and ordinary tools remain ordered. Each delegated mission carries an explicit capability statement — its exact, sorted toolset, the boundary that nothing else is available, and a report contract to flag ambiguity or architectural choices back to the caller rather than deciding them (tuned to DeepSeek's mechanical-worker strengths).

`run_subagent` takes an optional `role` argument, so the model names each run for the job it does (`auth-flow-mapper` rather than a bare `general`). The transcript chip shows the role, falling back to the free-form title. The name is **display and handoff only**: the cache pin, the stable per-kind system message, and the context record's `Kind` all stay keyed on the fixed capability class, so a model inventing a novel role name can never fragment the provider cache.

Since feature 012, the subagent system message is per-kind-per-session **stable** (kind identity + workspace + capability statement) and the per-run HANDOFF CONTRACT rides the first user message — so every dispatch of a kind reuses the provider-cached system+tools prefix instead of cold-writing it. Completed runs persist a verbatim context record (transcript, end-of-run touched-set fingerprints, terminal shape) under the session's `agents/` sidecars. A continuation dispatch — the next step of the same task, a related same-session follow-up, or the review of a just-finished implementer — replays its predecessor's transcript byte-for-byte on the same pin and appends one user message; the provider bills the shared prefix as cache reads, verified per dispatch from provider-reported fields (`link: continued (…) — cache: N% reused`, or an honest `linked but cold` when the cache was gone). Staleness uses end-of-run fingerprints (a run's own edits are never stale) with a majority-decline threshold; blocked links fall back to a digest-seeded fresh start, recorded with their reason. Review continuations keep the implementer's wire tool array (cache identity) while the harness refuses mutations. `contextLinking=off` restores pre-012 behavior exactly.

v1.1.0 adds a **session-long execution chain**. Because the `general` agent now makes every change, the workspace is its shared subject and consecutive tasks are related by construction — so its chain continues across tasks in a session without the relatedness bar, recorded with the link reason `session-chain`. The second change through the same executor is billed largely as cache reads rather than a cold prefix. `explore` and `review` keep the relatedness requirement, since two unrelated explorations genuinely share nothing. Every other feature-012 guard is unchanged: staleness fingerprints, terminal shape, window fit, replay drift, and model identity all still block a link and fall back to a digest-seeded fresh start with its reason recorded.

Nothing counts runs. A dispatch is refused only for a reason the model can act on — an unknown kind, a scope violation — never because a number ran out, and no report tells the model how many runs it has left. One-at-a-time is not a refusal either: a batch of `run_subagent` calls executes serially (every delegate announced up front so the queue is visible rather than looking frozen), which is also the cheapest order, since each dispatch can continue its predecessor's cached stream. What keeps a run bounded is internal to the run: its own turn limit, its optional provider-reported token ceiling, and the wrap-up that turns a breach into a `partial` label instead of silent truncation. What keeps a *task* bounded is the liveness set that predates delegation entirely.

## Model roles and the session advisor

The user never manages models. `/model` is gone, and so is every model name in the TUI chrome. Three roles exist instead:

- **MAIN** — plans, analyzes, and instructs. Default MiniMax M3.
- **EXECUTION** — does all the work, inside subagents. Default DeepSeek V4 Pro.
- **UTILITY** — cheap auxiliary calls (the advisor, onboarding). DeepSeek V4 Flash, resolved from the gateway catalog by name with a fallback to the configured subagent model, so a catalog without a Flash-class entry still works instead of failing.

**Models are frozen for the session.** Caching is the reason: a mid-session switch cold-starts the main prefix *and* breaks the execution chain's continuation, which is precisely what this architecture exists to protect. So the **session advisor** runs at most once, on the first prompt of a session, before the first main request — the only moment when a switch is free because nothing is cached yet. It is a small utility-model call (200 max tokens, 8-second timeout, its own `:sub:advisor` pin) that sees the configured pairing, the catalog with each model's window/family/continuation support, a one-line workspace size signal, and the prompt. Its expected answer is `keep`; it exists for the case where a session's first task obviously outgrows the configured main model. Every failure mode — disabled, empty catalog, timeout, malformed answer, unknown model id, apply error — silently keeps the configured models. The advisor must never be a point of failure; a session that starts is worth more than a marginally better model.

Mid-session, genuinely different large work does not switch anything. It gets one advisory notice instead — *"/new would give it a clean start and a fresh cache"* — emitted at most once per session, costing no model call and blocking nothing.

Escape hatches: `muhiyacode config set model <id>` and `config set subagentModel <id>` pin the roles (a pinned pair disables the advisor outright), and `config set advisor off` disables it directly. A 24-hour TTL refresh keeps the gateway model catalog current so the advisor and the role defaults resolve against real entries.

## Regression gates

Tests enforce prompt-size ceilings, stable prompt bytes, lite-tool isolation, history folding/intactness, range coverage and migration fixtures, effort/class budgets, bounded outputs, subagent limits/reuse, steering, final landing, and real streamed integration turns. v1.1.0 adds coverage for the execution role gate and its carve-outs (`rolesplit_test.go`), checklist parsing and the completion disclosure (`checklist_test.go`, `completion_audit_test.go`), and the advisor's once-per-session firing and silent failure modes (`advisor_test.go`). The field-test fixes add two more: `subagent_dispatch_test.go` pins that no turn — `chat` included — can be starved of a legal action, and `fieldtest_e2e_test.go` replays the owner's actual transcripts end to end, including the trust-the-report case, which asserts on the **main** stream's reads only (the executor's own reads ride a `:sub:` pin and are legitimate — it must read a file before changing it).
