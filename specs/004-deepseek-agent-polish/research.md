## Part A — Current-state evidence (codebase)

**A1. Plan state is two booleans plus per-step statuses; no whole-plan lifecycle exists.**
`Engine.planMode` / `Engine.pendingPlan` ([engine.go:132-133](../../internal/orchestrator/engine.go)) persist via `PlanStateSnapshot{PlanMode, PendingPlan}` → `plan_state.json` ([types.go:302-305](../../internal/contract/types.go), [session.go:235](../../internal/state/session.go)). `contract.Plan` is `Steps/Note/UpdatedAt` only ([types.go:278-282](../../internal/contract/types.go)); `PlanStep.Status` ∈ `pending|in_progress|completed` ([types.go:265-276](../../internal/contract/types.go)). Plan content persists to `plan.md`/`tasks.md` via `WritePlan` ([session.go:160-170](../../internal/state/session.go)) and is **never cleared** — no `ClearPlan` exists; `e.plan` is only ever overwritten by `updatePlan` ([engine.go:1581](../../internal/orchestrator/engine.go)) or session reload ([engine.go:260](../../internal/orchestrator/engine.go)).

**A2. Root cause of the stale "still executable" hint.**
`pendingPlan` is cleared in exactly two places: the "Proceed now" modal choice ([actions.go:615](../../internal/tui/actions.go)) and a user message matching the **anchored** `continuationRE` `^(continue|go (on|ahead)|proceed|…)[\s!.?]*$` ([classify.go:45](../../internal/orchestrator/classify.go), consumed at [engine.go:649-655](../../internal/orchestrator/engine.go)). Any natural phrasing ("proceed with the plan", "yes, build it") misses the anchor: the plan executes to completion but `pendingPlan` stays `true`, `plan_state.json` survives (`ClearPlanState` only fires when both flags are false, [plan.go:71-77](../../internal/orchestrator/plan.go)), and every launch/resume re-emits *"Saved plan pending — say 'proceed' (or 'go ahead') to execute it."* ([engine.go:293](../../internal/orchestrator/engine.go) → [root.go:87-93](../../internal/command/root.go), [actions.go:533-535](../../internal/tui/actions.go)). Compounding: `maybeSignalPlanReady` ignores step completion ([plan.go:108-117](../../internal/orchestrator/plan.go)); the plan-progress line renders a fully-completed plan indefinitely ([view.go:218-232](../../internal/tui/view.go)); the task finalizer never touches plan state ([engine.go:595-630](../../internal/orchestrator/engine.go)).

**A3. Hint surfaces inventory.** Startup notice ([engine.go:293](../../internal/orchestrator/engine.go), shown [root.go:87](../../internal/command/root.go)); mid-TUI resume notice ([actions.go:533](../../internal/tui/actions.go)); transient "Plan saved…" notify ([actions.go:625](../../internal/tui/actions.go)); one-shot finalize answer ([engine.go:1014](../../internal/orchestrator/engine.go)); modal descriptions ([actions.go:607-609](../../internal/tui/actions.go)); plan-progress line ([view.go:218-232](../../internal/tui/view.go)); footer "· plan mode" ([view.go:269-271](../../internal/tui/view.go)).

**A4. Tool schemas are never filtered by mode — by design, for the cache.**
`sessionDefinitions()` always emits the full base + synthetic + MCP set ([engine.go:1055-1069](../../internal/orchestrator/engine.go)); the design comment ties the session-stable tool block to DeepSeek's implicit prefix cache. Restriction is per-turn prose (plan block [plan.go:123-135](../../internal/orchestrator/plan.go); task-brief `agents=0 (no run_subagent)` [classify.go:150-153](../../internal/orchestrator/classify.go)) plus execution-time gating. Subagents share the same gate with an `allowed` set ([subagent.go:155,176](../../internal/orchestrator/subagent.go)).

**A5. Confirmed mode/enforcement gaps** (input to the D8 audit):
1. Every `mcp__*` tool is treated as mutating ([subagent.go:295](../../internal/orchestrator/subagent.go), [inspection.go:198](../../internal/orchestrator/inspection.go)) → read-only MCP tools are blocked in plan mode with *"MCP tools are unavailable in plan mode."* ([engine.go:1419](../../internal/orchestrator/engine.go)). MCP tool annotations (`readOnlyHint`) are **not captured** anywhere in `internal/mcpclient` (grep-verified).
2. Unknown tools get bare `"unknown tool %s"` ([registry.go:150](../../internal/orchestrator/registry.go)) — no nearest-name hint; unknown-tool args are never validated ([engine.go:1155-1157](../../internal/orchestrator/engine.go)).
3. `run_subagent` at `agents=0`: the hard "closed for the rest of this task" message only appears on the **second** denial ([subagent.go:95-98](../../internal/orchestrator/subagent.go)).
4. `propose_changes` without an interactive client silently returns an auto-approved verdict ([engine.go:1618-1619](../../internal/orchestrator/engine.go)) — the model is told "approved" though no human approved.
5. Duplicate-read blocks return `Failed:false` ([engine.go:1442-1444](../../internal/orchestrator/engine.go)), so they feed none of the failure breakers; only the repeat limiter catches a re-read loop.
6. Permission/trust denials reach the model as generic `"Tool %s failed: workspace: permission denied"` ([engine.go:1455](../../internal/orchestrator/engine.go)) with none of the approver-side context.

## Part B — DeepSeek V4 external research (Principle VII)

Credibility tiers: **T1** official DeepSeek docs/model card/paper · **T2** reputable press/benchmark orgs · **T3** community (GitHub issues, HN, practitioner guides). Full source index at the end of this part.

**B1. Family and IDs (T1).** DeepSeek-V4 public preview 2026-04-24 (MIT, open weights); official release mid-July 2026. Two variants, one API: `deepseek-v4-pro` (1.6T/49B-active MoE) and `deepseek-v4-flash` (284B/13B-active), both 1M context, 384K max output. Both are **hybrid thinking models** — no separate chat/reasoner; thinking on by default, controlled by `thinking: {type}` + `reasoning_effort` (`low/medium`→`high`, `xhigh`→`max`; two real levels). **Legacy `deepseek-chat`/`deepseek-reasoner` are retired 2026-07-24** (currently aliases). Sources: api-docs.deepseek.com/news/news260424, /guides/thinking_mode, /updates; huggingface.co/deepseek-ai/DeepSeek-V4-Pro.

**B2. Cache economics dominate (T1).** Off-peak per-M-token input: Flash $0.0028 hit vs $0.14 miss (**50×**); Pro $0.003625 vs $0.435 (**120×**). Automatic disk-based prefix caching; 64-token cache units (shorter fragments buy nothing); cleared after hours-to-days idle; usage reported as `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens` (already parsed, A10). Peak/off-peak 2× multiplier lands with the official release (9:00–12:00, 14:00–18:00 Beijing) — T2 (TechNode 2026-06-30). Community-reported agent hit rates: ~70% (sloppy harness) to 98.6% (disciplined) — T3 (HN). Implication: byte-stable append-only prefixes are worth more than any other optimization; benchmark cost comparisons must control for the pricing window.

**B3. Capability shape (T1 card + T3 reviews).** Pro (Max): SWE-bench Verified 80.6%, SWE-bench Pro 55.4%, Terminal-Bench 2.0 67.9%, LiveCodeBench 93.5%; Flash ≈1.6 pts behind on SWE-V. Strong mechanical/iterative coding; weaker on hard cross-repo work. Text-only (no vision). **High answers-anyway rate** (~94–96% on abstention metrics — T3) and community-documented **premature completion claims / shortcut-seeking on long tasks** (T3, HN). Implication: harness-side verification gates, not model self-report, must terminate tasks (feeds D6); external progress tracking (plan steps) matters (feeds D1).

**B4. Tool-use behavior (T1 + T3).** Max 128 tool definitions. **Tool `description` quality is the primary steering surface** ("tighter reasoning over tool selection"); `tool_choice:"auto"` recommended. **Known wire quirks:** (i) in thinking mode `tool_choice:"required"`/named-function returns HTTP 400 (T3 GH#1376, corroborated by docs note) — only `auto`/`none` are safe; (ii) tool calls intermittently emitted as plain text inside `content` (~11% in a 40-tool streaming session, sometimes Chinese-prefixed) — T3 GH#1244; (iii) intermittent zero-token empty completions (HTTP 200, `content:""`, `completion_tokens:0`) specifically after tool results under streaming+tools; plain retries reportedly can fail — T3 GH#1453. Strict-schema mode exists but is beta-gated (`/beta` base_url, all-required + `additionalProperties:false`, no `minItems/maxItems`). Implications: keep `tool_choice` pinned `auto` (already true, A9); budget a permanent salvage/repair layer (D5); treat zero-token completions as a distinct retryable class (D5); invest in tool descriptions (D10); don't adopt strict mode through a generic gateway (degradation risk).

**B5. Instruction-following (T1 + T3).** In thinking mode `temperature/top_p` are silently ignored; penalties deprecated API-wide — determinism must come from prompt structure and validation, not sampling. Practitioner consensus (T3, convergent across three guides): long system prompts get under-weighted in reasoning mode; put operative task directives in the **user message**; recap hard constraints at the **end** of the prompt; prefer positive framing; avoid instruction overload. JSON-output mode requires the literal word "json" in a message. DeepSeek auto-escalates "agent-shaped" traffic to `max` reasoning — pin `reasoning_effort` explicitly (already sent explicitly, A10). Implication: MuhiyaCode's architecture (lean static prefix + per-turn operative brief on the user message tail) is **exactly the right shape** — validated, not changed (D4); the dedup/priority pass tightens rather than restructures.

**B6. Thinking-mode replay requirement — empirically unresolved (T1 + T3, conflicting).** Docs + an OpenClaw issue (multi-turn subagent chains) indicate thinking mode requires `reasoning_content` passed back on tool-call chain turns, and that **empty string or omission can return HTTP 400**. MuhiyaCode today replays an **empty-string** key on DeepSeek assistant tool-call turns ([provider.go:284-288](../../internal/gateway/provider.go)) and live evidence (001) ran clean against `deepseek-v4-flash` through the MuhiyaLLM gateway. The behaviors conflict (gateway normalization, model rev, or mode differences may explain it). Resolution: **verify empirically against the live launch endpoint before any related change**; contingency documented in D5. Sources: api-docs.deepseek.com/guides/thinking_mode; github.com/openclaw/openclaw#72044.

**B7. Delegation (T3).** Community pattern: Pro as planner/orchestrator, Flash as workers; MCPAtlas 73.6 (Pro). Worker-mode evidence (deepseek-as-subagent): strong at mechanical batch work with **self-contained, explicit briefs**; weak at cross-file architectural judgment; don't delegate trivial single-file work. Orchestrator-mode failure: premature "task complete". Implications: subagent briefs must state exact toolset + mechanical scope (D3/D10); completion verification (D6); MuhiyaCode's separate subagent session pin (`:sub`, A10-adjacent) already matches Reasonix's session-fork pattern.

**B8. Reasonix reference (T1 listing + T3 repo).** esengine/deepseek-reasonix: third-party but officially documented DeepSeek-native terminal agent (single static Go binary, MCP stdio plugins). Its cache design: (1) small stable startup injection; (2) append-only cache-first loop; (3) pruning only at compaction boundaries; (4) **versioned tool-schema contract under regression review** (drift tests); (5) flash-first routing with **session-forked** escalation; (6) **automatic tool-call repair** as a permanent component. MuhiyaCode already implements 1–3 (002) and 4 (PrefixShape + marshal-determinism tests); 5 is satisfied by per-model session pins; 6 exists as `NeedsToolCallRescue` but its coverage needs an audit against B4's failure modes (D5). Community-verified 97–98.6% hit rates under this design (T3).

**B9. API surface notes (T1).** OpenAI-compatible ChatCompletions (+ an Anthropic-compatible endpoint, unused here); function calling, JSON mode, logprobs, ≤16 stop sequences; `frequency_penalty`/`presence_penalty` deprecated; **no documented `parallel_tool_calls` param**. Version churn is fast (V3.2→V4 in ~5 months) — pin concrete model IDs, re-verify quirks per release ([docs/prompt-caching.md](../../docs/prompt-caching.md):8-9 already recommends a concrete `deepseek-v4-flash` pin).

**B10. What this validates about the existing design.** The 50–120× hit/miss spread (B2) retroactively justifies constitution III/IV and 002's whole architecture; B5 validates the per-turn-rider placement; B8 confirms the reference architecture is already substantially adopted. 004's DeepSeek work is therefore **targeted hardening** (salvage coverage, empty-completion class, replay verification, description quality, honesty gates), not restructuring — consistent with Principle VIII.

## Part C — Decisions

### D1 — Plan lifecycle: an explicit phase machine at existing choke points

**Decision**: Introduce a single plan-level lifecycle field `Phase` ∈ `{none, drafting, ready, pending, executing, finished, interrupted, superseded, discarded}` carried in `PlanStateSnapshot` (additive JSON field `phase`; legacy snapshots derive `pending`→`pendingPlan:true`, `drafting`→`planMode:true`, else `none`). Transitions are wired **only at existing choke points**: `updatePlan` (first step marked while `pending/ready/interrupted` and plan mode off → `executing`; edits while plan mode on → `drafting`), plan-ready resolution (→ `ready`, then modal: Proceed now → `executing`, Proceed later → `pending`, Keep planning → `drafting`), pending-plan brief injection (→ `executing`), `finalize` (executing + all steps `completed` → `finished`; executing + incomplete steps → `interrupted`, wording keyed on `TaskStats.StopCause`), plan-ready over an existing `pending/interrupted` plan (old → `superseded`), and a new `/plan clear` action (→ `discarded`). Execution-start detection is therefore **step-progress-driven** (any run that starts completing plan steps is executing) with the continuation-phrase path kept as an accelerator and widened from an anchored full-match to a word-boundary match over a short phrase list ("proceed with the plan", "go ahead and …", "execute the plan"). Every hint surface (A3) becomes phase-keyed: executable hints render **only** in `pending`; `interrupted` gets resumable-partial wording ("plan partially executed — N/M steps done; say 'proceed' to resume"); the progress line hides in `finished/superseded/discarded/none`; `maybeSignalPlanReady` additionally requires ≥1 incomplete step.

**Rationale**: A2 shows the defect is structural — two booleans cannot represent "was executed"; every fix that keeps inferring from them re-creates the ambiguity. One enum field, persisted in the existing sidecar, transitions only where state already changes (VIII: smallest change), gives every UI surface a single truth source (FR-001..005), and survives resume by construction (FR-004). Step-progress-driven detection closes the natural-phrasing hole without brittle NLU: executing is defined by what happens (steps advance), not by how the user phrased consent. B3's premature-completion evidence reinforces phase-from-recorded-state over phase-from-model-claims.

**Alternatives considered**: (a) *Just widen the regex* — rejected: still utterance-inferred; "run the plan now please" variants are unbounded, and the finished/interrupted distinction stays unrepresentable. (b) *Clear `plan.md` on completion* — rejected: destroys the user's plan record and doesn't fix pending-flag truthfulness. (c) *Multi-plan archive with IDs* — rejected: MuhiyaCode has exactly one active plan by design; an archive is a rewrite (VIII) serving no spec requirement (supersede semantics cover replacement). (d) *LLM-classified execution intent* — rejected: adds per-turn cost and nondeterminism to a correctness path (I).

### D2 — Terminal states: end-of-task reconciliation sweep

**Decision**: Two-layer guarantee for FR-013. **Engine layer**: the tool dispatch path guarantees a `ToolEnd` for every `ToolStart` (defer-based emission on cancellation/error paths), and subagent runs guarantee a terminal `done` event with a status. **TUI layer** (safety net): when a task finishes (existing task-complete/stats message), sweep the transcript and mark any `toolView` still `"running"` as `"cancelled"` and any `agentView` still `"running"` as `"cancelled"` — rendered with a neutral terminal glyph, never left animating. Plan steps are **not** auto-completed (they stay model-owned); instead the plan phase records `interrupted` (D1) so the display is truthful without fabricating step completion.

**Rationale**: A6 shows two independent stick-at-running paths; fixing only the emitters leaves unknown future paths open, fixing only the TUI leaves headless runs (`root.go`) unreconciled — both layers together give SC-004's 100% terminal-state guarantee cheaply. Auto-completing steps would violate honest reporting (VI, in spirit) and mask real interruption.

**Alternatives considered**: timeout-based watchdogs per tool row (rejected: masks real hangs, adds timers to the render path); marking stuck items `"fail"` (rejected: "cancelled" is truthful; "fail" fabricates an error that didn't happen).

### D3 — Mode awareness: full schemas stay; awareness rides per-turn; enforcement gets precise

**Decision**: Keep the session-stable full tool schema set (no per-mode filtering) — constitution III and B2 make schema stability non-negotiable. Improve **awareness** on the existing dynamic surfaces: (a) subagent mission briefs gain an explicit capability statement — a deterministic, sorted "Tools available to you: …; anything not listed is unavailable to you" line plus the mission boundary sentence (composed from `spec.Allowed`); (b) the plan block and task-brief keep carrying main-loop restrictions (already present, A4) with wording aligned to one taxonomy. Improve **enforcement** at the existing gate: (1) plumb MCP `annotations.readOnlyHint` through `mcpclient` (captured at `tools/list`, default absent→mutating) and let plan mode allow read-only-annotated MCP tools, replacing the blanket block (A5.1); (2) unknown-tool feedback gains a nearest-name suggestion over the offered set ("unknown tool X. Closest available: Y") (A5.2); (3) `run_subagent` when the task budget is zero returns the hard "closed for this task — do NOT call it again" message on the **first** denial (A5.3); (4) `propose_changes` in non-interactive runs labels its verdict honestly ("auto-approved by non-interactive policy — no human reviewed this") (A5.4); (5) permission-denial feedback names the denial class (outside-workspace / protected-credential-path / user-declined / unread-overwrite) in one added clause (A5.6). All strings live in the mode-capability contract as the reviewed catalogue.

**Rationale**: FR-008..011 demand both halves — being told and being stopped. Per-turn riders are the constitutionally correct awareness channel (IV) and B5 says they're also the channel DeepSeek actually weights. Each enforcement fix is a bounded change at an existing decision site (VIII). `readOnlyHint` is the one new plumbing item; without it, plan mode over-blocks legitimate read-only MCP tools, which manufactures exactly the out-of-mode retry loops US3 is meant to eliminate — defaulting absent annotations to mutating keeps the security posture (IX).

**Alternatives considered**: (a) *Filter schemas per mode* — rejected: violates III, busts the DeepSeek prefix cache every toggle (B2: 50–120× cost cliff), and 002's architecture explicitly rejected it. (b) *A second system-prompt "current mode" section* — rejected: mode is per-turn dynamic; placing it in the prefix violates IV and invalidates cache on every toggle. (c) *Trust-annotation-free MCP heuristics (name sniffing "get_/list_")* — rejected: guessable, unsafe (IX); annotation-or-mutating is deterministic.

### D4 — Prompt: dedup/priority tightening pass, not a rewrite; net size ≤ current

**Decision**: One structural editing pass over `SystemPrompt()` within the existing 9-section order: (a) add a single instruction-priority line to the OPERATING CONTRACT ("when rules conflict: safety > user's explicit request > this contract > style"); (b) remove duplication between OPERATING CONTRACT rule 5/6 and COMMUNICATION (verify-then-stop / final-answer phrasing appears in both); (c) fold TOOLS AND RECOVERY overlap with CACHE DISCIPLINE's re-read prohibition into one home; (d) keep the DeepSeek addendum and extend it by one sentence covering completion honesty ("Report only work actually performed; if steps remain, say so"), paid for by the dedup savings so **net estimated tokens ≤ today's ~1,900**. The change ships as a one-time prefix version bump: stability fixtures (`prompt_stability_test.go`, `restart_determinism_test.go`, `cachehit_guard_test.go`) updated in the same commit; a live before/after benchmark (D9) validates no hit-rate or quality regression. Section **order is preserved** (identity/contract first, environment last) — B5's "directives late" guidance is already satisfied by the per-turn brief riding the user-message tail, so no order churn is warranted.

**Rationale**: FR-018 asks for explicit priority, dedup, and no growth; A8 shows the prompt is already lean and correctly layered, and B5 validates the layering — so the highest-value, lowest-risk move is tightening in place (VIII). The addendum is the model-family-conditional slot that exists precisely for model-specific behavior (completion honesty targets B3's documented weakness at the cheapest possible token cost). Any prefix-byte change invalidates existing sessions' caches once — acceptable and unavoidable for *any* prompt improvement; new sessions re-prime immediately (II justification recorded here per the workflow gate).

**Alternatives considered**: (a) *Reorder sections per DeepSeek folklore* — rejected: no T1 evidence for intra-system-prompt position sensitivity (B5 covers system-vs-user weighting, which we already exploit); order churn maximizes diff risk for zero verified gain (X). (b) *Move more instruction mass into per-turn riders* — rejected: violates 002 SC-004's ≤~50-token tail invariant and V (retransmission every turn beats cached-once). (c) *A per-mode prompt variant* — rejected outright: III forbids per-request prefix switching.

### D5 — DeepSeek wire robustness: verify replay, harden salvage, classify empty completions

**Decision**: Three bounded work items in the gateway layer. (1) **Replay verification first** (blocking gate for this group): a live probe through the MuhiyaLLM gateway exercising a multi-turn tool-call chain in thinking mode, asserting whether the current empty-string `reasoning_content` replay ([provider.go:284-288](../../internal/gateway/provider.go)) is accepted by `deepseek-v4-pro`/`-flash`. If accepted → keep (document as verified). If rejected (B6's 400) → contingency: store `reasoning_content` per assistant tool-call turn in the active task window and replay it verbatim (append-only, folded at settled boundaries like other completed-task payloads; prefix-safe because history only appends). (2) **Salvage coverage audit + hardening** of the `NeedsToolCallRescue` path against B4's documented failure shapes: JSON-tool-call-in-content, DSML markup, language-prefixed text before the call; salvage bounded to one repair attempt per turn, each repair recorded as a wire event (VI: observable, not silent). (3) **Zero-token empty completion class**: a 200 stream that yields no content, no tool calls, and `completion_tokens==0` after a tool-result turn is classified as a distinct retryable wire failure (one immediate same-request retry, then one nudge rider, then honest surface — reusing the existing empty-final bound rather than adding a new loop). `tool_choice` stays contractually pinned to `auto`/`none` (A9 already enforces; the contract makes it a reviewed invariant given B4's thinking-mode 400). Model-ID hygiene: audit configs/docs for legacy `deepseek-chat`/`deepseek-reasoner` references (retire by 2026-07-24, B1).

**Rationale**: FR-016/FR-020 name retry behavior, error recovery, and tool-result handling as review targets; B4/B6 supply the concrete, sourced failure modes. Verification-before-change on replay honors X and avoids building the heavier contingency on an anecdote; the salvage layer is the Reasonix-validated permanent component (B8); the empty-completion class converts a documented silent-stall mode into a bounded, visible recovery path (FR-016).

**Alternatives considered**: (a) *Preemptively implement full reasoning replay* — rejected: unverified against the live gateway (X), grows every request's payload, and complicates folding for a failure we may not have. (b) *Strict-schema beta mode* — rejected: beta base_url through a generic OpenAI-compatible gateway violates IX's graceful-degradation requirement; schema normalization cost buys nothing until the gateway exposes it. (c) *Client-side automatic session restart on empty completions* — rejected: destroys the warm prefix (B2) on an unproven remedy; bounded retry + honest surface is cheaper.

### D6 — Completion integrity: reconcile the final answer against recorded state

**Decision**: A completion audit inside `finalize` for task classes ≥ standard, using only already-recorded facts (never an extra model call): (a) plan-phase stamping per D1 (finished vs interrupted); (b) when plan steps remain incomplete at finalize, append a harness-attributed disclosure line to the answer ("— 2 of 6 plan steps incomplete: …") instead of letting the answer imply completion; (c) when the answer claims checks/tests ran (small fixed pattern set) while `stats.ChecksRun == 0`, append "(note: no checks were run this task)"; (d) the `"Done."` default for empty answers is replaced by the existing `fallbackAnswer` synthesis plus the disclosure machinery. The audit never blocks finalize and adds no turns.

**Rationale**: FR-017 requires claim/record reconciliation; A7 shows all inputs (DoneCriteria, FilesChanged, ChecksRun, step states) already exist unreconciled; B3 documents the model-family weakness (answers-anyway 94–96%, premature completion) that makes this the single highest-leverage honesty mechanism for launch. Harness-attributed appends keep VI-style honesty without censoring or rewriting model text.

**Alternatives considered**: (a) *LLM-judge verification pass* — rejected: adds cost/latency to every task and nondeterminism to a correctness surface (I); pattern-scoped reconciliation of recorded facts is deterministic. (b) *Block finalize until steps complete* — rejected: the 8-continue nudge budget already exists; hard-blocking manufactures loops on genuinely blocked tasks (the honest outcome is disclosure, not coercion).

### D7 — Tool rows: `apply_patch` target + filename-preserving truncation

**Decision**: Two deltas completing 003's tool-display contract (A13): (1) `toolTarget` learns to derive `apply_patch`'s target from the patch argument's first `+++ b/<path>` (or `+++ <path>`) header — first file wins, with a ` (+N files)` suffix when the patch touches more than one; (2) a `truncateMiddle` helper (keeps path head and filename tail around a single ellipsis glyph) replaces head-anchored `oneLine` for the target segment in `renderTool`, so long paths keep their filename and never push the `+N −N` counts off-row. Tests follow the existing conventions (`stripANSI` substring + ordering assertions; U+2212 minus).

**Rationale**: FR-006/FR-007; A13 shows the general layout already exists — these are the only two gaps between code and the already-agreed 003 contract (which specifies "file path (middle-truncated)" for exactly these tools). Smallest possible UI change (VIII); no prompt/prefix surface touched (cache-inert).

**Alternatives considered**: storing raw args on `toolView` for render-time parsing — rejected: target derivation at tool-start is the existing pattern; keeping derived strings only is lighter and already test-covered.

### D8 — The audit is a versioned artifact seeded from Part A, closed by fixes or rationale

**Decision**: `specs/004-deepseek-agent-polish/audit.md` is created at implementation start, seeded with every confirmed finding from Part A (A2, A5.1–A5.6, A6, A7, A9's degraded-path note, plus D5's wire risks), each entry carrying: symptom → root cause (file:line) → disposition (fix task ID | deferred + rationale). The audit closes only when every entry has a disposition and fixes link to their verification evidence; the FR-012 category list (orchestration failures, invalid tool calls, incorrect mode transitions, delegation problems, unfinished task states, repeated work, unnecessary tool usage) is the completeness checklist — each category must cite at least the findings above or an explicit "no defect found" sweep note.

**Rationale**: FR-012/SC-009 require a documented audit with 100% disposition; Part A already *is* the audit's first pass (evidence-grade, file:line), so the artifact formalizes and tracks it rather than re-discovering it. Deferrals stay honest and reviewable (VI in spirit).

**Alternatives considered**: tracking findings only as tasks in tasks.md — rejected: loses the category-completeness view and the deferral rationale record SC-009 demands.

### D9 — Measurement: capture the missing baselines first, then identical-config afters

**Decision**: Because prefix-stability and cost baselines were never captured (A12), the implementation sequence is measurement-first: (0) **Baseline run before any behavior change** — `benchmarks/cachebench` live against the launch gateway/model, scenarios `coding-session` + `fat-context`, N≥3, price flags supplied, recording steady-state hit rate, prefix-stability rate (`new_tail_tokens` now exists), tokens, cost, plus the new scripted suites' baseline failure evidence (plan-lifecycle, mode-scenario, completion, terminal-state tests — expected red where they codify current defects). (1) After implementation: identical config, back-to-back with matched time-of-day (B2's peak-pricing 2× makes token counts the primary cost comparator; the recorded pricing window contextualizes dollar figures). Gates: prefix stability ≥99% every run (001 SC-001 definition; 002's ≥99.5% aspiration recorded alongside); steady-state hit rate ≥ baseline within 1.0 pp variance; median tokens and cost per completed task ≤ baseline; scripted suites 100% green; every SC-001..009 acceptance path exercised in quickstart.md. Evidence lands under `specs/004-deepseek-agent-polish/benchmarks/`.

**Rationale**: X requires realistic before/after with everything but the change held constant; without a fresh baseline the feature literally cannot make a verifiable claim (VI). Scripted-suite "red baselines" convert the reported defects into regression-proof evidence of the fix.

**Alternatives considered**: reusing 001's 96.57% figure as the baseline — rejected: 001's own research marks it invalid for verdicts (missing stability data, wrong denominator context) and it predates 002/003 changes; comparing against it would be dishonest measurement (VI).
