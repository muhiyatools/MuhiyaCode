# Phase 0 Research: Subagent Context Reuse & Cache-First Orchestration

**Feature**: 012-subagent-context-cache · **Date**: 2026-07-19
**Method**: six parallel forensic readers over both repos (agent + gateway) and provider documentation, followed by an adversarial completeness critic that verified cross-reader contradictions against live code. 144 anchored facts collected; the load-bearing subset is recorded here. All anchors were verified against code at commit `e163506`.

---

## 1. Forensic findings (the system as it actually is)

### 1a. Subagent lifecycle — what exists (R-F1–R-F4)

- **R-F1 — A subagent is born as exactly two messages and dies without a trace.** System message = `"You are the <kind> subagent inside MuhiyaCode. "` + spec.System + workspace path + capability statement + the rendered five-field HANDOFF CONTRACT (Role/Scope/Context/Deliverable/OutputFormat); user message = the task verbatim. On return, the local `messages` slice is discarded — **no subagent transcript survives anywhere** (no `AppendTranscript` call exists in subagent.go). The only durable remains: a 4000-char-capped `run_summary` SQLite event, a 4000-char-capped knowledge `Full` entry, and a 2200-char parent-visible digest. [subagent.go:254-255, 41-86, 193-224; knowledge.go:57-72]
- **R-F2 — Sequential dispatches share almost nothing.** Three channels only: a ≤1500-char scope-keyword-matched briefing (6 facts × 320-char digests + ≤12 file names), exact-TaskKey report reuse (explore/plan only, same edit-epoch), and the shared workspace. No messages, no provider context, no sibling awareness. The briefing's keyword matcher needs a ≥4-char lexical overlap — paraphrased follow-ups get the "no overlap" boilerplate. [subagent.go:132-143, 249-252; knowledge.go:74-85, 142-205]
- **R-F3 — Discovered defect: every dispatch cold-writes its provider prefix today.** The per-run handoff (Scope = task text) lives **inside the system message**, so two runs of the same kind never share a prefix beyond byte 0 divergence — the feature-011 per-kind pins (`:sub:<kind>`) keep gateway *routing* stable, but the provider prefix cache they were meant to keep warm is busted by design on every dispatch. Reader 1 raised this as an open question; the critic and the message-composition anchors confirm it. This is the single largest measured-waste candidate the feature must fix. [subagent.go:248-255, 343]
- **R-F4 — Kind taxonomy and tool surfaces.** Kinds: explore(12)/plan(14)/review(14) on the 8-tool read-only set; general(24) on the full registry. Turn caps scale by effort (×0.75–1.4). TokenCeiling exists but is dormant (`reviewAbsoluteCapBase = {0,0}` pending T021), so ceiling wrap-up machinery never fires in production. Kind system prompts are 1–2 sentences; synthetic tools are structurally unreachable from subagents. [subagent.go:88-107; reviewgate.go:206-231; definitions.go:15-25]

### 1b. Replay determinism — continuation is provably feasible (R-F5–R-F9)

- **R-F5 — DeepSeek replay is frozen byte-exact by golden test.** `ReasoningReplayStrip` nils reasoning on every replayed message (re-adding the required empty `reasoning_content` key only on assistant tool-call turns); the golden pins the exact bytes, and a second test proves settled replay bytes are **identical across live effort levels**. Strip is deterministic and idempotent → replaying a stored transcript reproduces previously-sent bytes exactly. [gateway/provider.go:298-320; replay_policy_test.go:35-49; marshal_determinism_test.go:74-87]
- **R-F6 — MiniMax replay is append-stable by test.** `ReasoningReplayPreserve` keeps `reasoning_details` as raw `json.RawMessage`; the determinism test proves that appending a user message to a settled transcript preserves the previously-sent prefix byte-identically. Constraint: persisted messages must round-trip the raw bytes without re-encoding. [marshal_determinism_test.go:89-108; contract/types.go:112-118]
- **R-F7 — Whole-request marshal determinism is already tested** (identical bodies for identical requests, byte-identical retry replays, frozen wire shapes for all four roles; JSON key order fixed by struct declaration). [marshal_determinism_test.go:15-58, 113-159]
- **R-F8 — One replay hazard: tool-result completeness.** `repairToolMessageSequence` runs on every replay; a transcript persisted with a missing tool result gets synthetic repair bytes injected at replay, breaking the prefix from that point. A continuation store must persist complete call/result pairings. [gateway/provider.go:329-366]
- **R-F9 — The prefix-stability guard already covers both loops.** Main loop: any settled-prefix change without a recorded invalidation event aborts the task. Subagent loop: any shape change after turn 1 fails the run. `PrefixShape` hashes the provider's *final replay representation* (`StableRequestMessages`), so a continuation design can extend the same guard. [turnloop.go:489-495; subagent.go:317-337; prefixshape.go:12-102]

### 1c. Pins, sticky routing, and cache accounting (R-F10–R-F13)

- **R-F10 — Wire pins are five, and docs lie.** Live pins: `:main` (turn loop + compaction), `:sub:{explore,plan,review,general}`, `:sub:onboarding`. No `:aux` wire pin exists (classification is heuristic-only); docs/prompt-caching.md documents pins that are not on the wire. **Code (feature 011 D4) is declared authoritative; the doc must be corrected in this feature.** [turnloop.go:320; maintenance.go:76; subagent.go:343; classify.go]
- **R-F11 — The gateway pins model routing per session pin**: `sha256(virtualKeyID|X-Muhiya-Session)` → routed model, in-process map, 24h TTL, 10k entries, lost on restart ("one cache-cold turn"). For OpenRouter upstreams only, the pin is forwarded as `X-Session-Id` (OpenRouter's documented sticky-routing key). **Continuations must reuse the predecessor's exact pin string** or forfeit both. [gateway repo proxy/stickysession.go:12-58; handler.go:994-1007]
- **R-F12 — Cache accounting is dual-dialect and honesty-hardened.** DeepSeek `prompt_cache_hit/miss_tokens` preferred; OpenAI `prompt_tokens_details.cached_tokens` fallback with derived miss (flagged). Rates consume only paired read+miss records; `PerPairingRates` groups by (model, pin) and excludes each pairing's first cache-reporting record as the cold write. A continuation that **reuses the predecessor's pin joins the existing warm pairing** — no new cold-write exclusion, so metrics stay honest without special-casing. [sse.go:228-324; contract/cache.go:66-124, 262-358]
- **R-F13 — Resume machinery precedent exists** for exactly this class of feature: `prefix_shape.json` sidecar (system/tools/model hashes, deliberately no history), resume-drift attribution, cold-start notices ≥8k tokens, and a free stale-resume prune (idle >6h ∧ history ≥20k ∧ yield ≥10%). Continuation cold-start honesty can reuse these patterns. [cacheresilience.go:18-185; contract/cache.go:389-403]

### 1d. Pipeline, plan persistence, and knowledge (R-F14–R-F16)

- **R-F14 — The plan is main-model property, unreachable by subagents.** Approved plan = in-memory `contract.Plan` + rendered markdown at `~/.muhiya/sessions/<id>/plan.md` (tasks.md is a write-only twin). That path is **outside the workspace**, and `Guard.ApprovePath` forces an interactive approval for outside-workspace reads in every permission mode; no plan-query or knowledge-query tool exists in the registry. Implement handoffs carry **only the group's numbered step titles** — no plan Note, no verification section, no research findings. [state/session.go:155-177; workspace/permissions.go:98-124; phaserunners.go:330-339]
- **R-F15 — Verified contradiction (critic): the planning-briefing delivery gap.** In the normal single-Run flow (research→planning mid-Run), the main model's planning turns receive only `"[research phase complete] N/M..."` — the 4000-char findings briefing fires only when a Run *starts* in planning (restart/park). The main model therefore plans from its own file reads today; a read gate imposed without fixing this would blind the planner. **Must be fixed as part of this feature.** [phaserunners.go:28-33, 100-106; turnloop.go:254]
- **R-F16 — Verified contradiction (critic): concurrent same-kind implementers already exist.** Harness fan-out runs multiple `general` implementers in parallel (effort-gated, path-disjoint groups); the serial restriction applies only to model-issued batches. Chain identity therefore **cannot** be "the one live stream per kind" — chains must be tracked per-run-lineage, with parallel dispatches forming parallel chains on the same pin (safe: provider caches are per-content, the pin only stabilizes routing). Also verified: the "partial (token ceiling) marks its group complete" risk is dead code today (ceilings are 0); the real hazard is **turn-exhausted wrap-up runs keep Status "done"** and are indistinguishable from clean completions in every durable record. [phaserunners.go:329, 341-349; dispatch.go:82-87; subagent.go:417-441]

### 1e. Read tracking and staleness primitives (R-F17–R-F18)

- **R-F17 — The predecessor's read-set does not exist as data.** Subagent dispatchScope deliberately runs with dedupe/trackStats off; subagent reads are recorded nowhere. The main-loop InspectionLedger records signatures + line coverage + an mtime/size fingerprint (no content hashing anywhere on the read path; staleness = lazy stat-compare consulted only on the next duplicate read). Full-ledger wipe on any shell mutation / apply_patch / MCP call. glob collects ModTime+Size and discards them at render. Inspection pathKey and knowledge canonicalKey normalize differently. [subagent.go:257-301; inspection.go:153-192, 317-335, 196-228; workspace/registry.go:151-155]
- **R-F18 — Duplicate reads are blocked (main loop only), not counted-only**; terminal reads (`cat/head/...`) are counted, never blocked, and prove models bypass read_file via the shell. The gate chain (`gatedExecute`) is the single shared chokepoint with a codified 5-clause gate policy (stated-in-advance, one-step-fixable, **bounded ≤2 identical rejections**, telemetered, sync-tested) and a documented failure precedent for allowlist-shaped gates. [gates.go:53-181; gatepolicy.go:1-41; reviewgate.go:437-463; shellclassify.go:9-28]

### 1f. Provider cache truth (web-verified 2026-07-19) (R-F19–R-F22)

- **R-F19 — DeepSeek**: context caching is automatic, disk-based, best-effort; identical-prefix matching from token 0 in **64-token blocks** (last partial block always misses); unused cache evicted "within a few hours to a few days"; usage reports `prompt_cache_hit_tokens`/`prompt_cache_miss_tokens`. Docs are **silent** on whether tools/top-level params join prefix identity and on whether the end-of-output cache-unit boundary makes a replayed final assistant turn hit-eligible. [api-docs.deepseek.com/guides/kv_cache]
- **R-F20 — MiniMax**: caching is passive/automatic, **≥512 input tokens required** (both repos already enforce this threshold), prefix order documented as **tool list → system → messages** (tool-list change kills everything after it), TTL load-adaptive and undocumented, hits reported as `prompt_tokens_details.cached_tokens` (miss derived, not reported). [platform.minimax.io text-prompt-caching]
- **R-F21 — OpenRouter**: implicit caching listed for DeepSeek et al.; **MiniMax appears on neither the implicit nor explicit list**; sticky routing after a cached request activates only when the provider's cache-read price is cheaper than input, keyed by `session_id`/`x-session-id` — exactly the header the gateway forwards. The gateway injects `cache_control` only for Anthropic-family targets; MiniMax-on-OpenRouter gets none. **The gateway repo seeds MiniMax as a DIRECT provider (api.minimax.io, migration 009); no OpenRouter-hosted MiniMax row exists in any migration.** The spec's "MiniMax through OpenRouter" premise is unverified against production and plausibly wrong or zero-cache. [openrouter.ai prompt-caching docs; gateway proxy/cache.go:74-126; db/migrations/009]
- **R-F22 — Exact continuation-hit conditions** (repo + docs, per provider): same pin string (routing + OR stickiness) ∧ gateway process alive (in-memory pin) ∧ byte-identical replay (guaranteed by R-F5/R-F6 given complete tool pairings and unchanged system/tools/model) ∧ cache not evicted. Then: DeepSeek bills everything up to the last previously-*sent* input as hits (64-token granularity); the predecessor's final assistant answer + new handoff bill as miss on the first continuation request *unless* the end-of-output boundary applies (open, probed in Phase A). MiniMax: same, ≥512-token floor, hits via `cached_tokens`. An effort change between runs alters top-level body params (`thinking`/`reasoning_effort`) — unknown cache effect on DeepSeek, probed.

### 1g. Reference architecture: DeepSeek Reasonix (Constitution VII) (R-F23)

- **R-F23** — Reasonix's cache-relevant layout, studied for feature 001 and re-examined here against current constraints: (a) one immutable system+tools prefix per role, per session — role variation expressed in the *first user message*, never the system prompt; (b) strictly append-only conversation growth with all per-turn dynamics at the tail; (c) explicit "settled boundary" beyond which nothing is rewritten. MuhiyaCode's main loop already conforms (Principles III–V machinery); the **subagent loop violates (a)** by embedding the per-run handoff in the system message (R-F3). This feature adopts (a) for subagents (R-D6) and its continuation design is a direct application of (b)/(c) to cross-run streams. Deviation retained: MuhiyaCode keeps per-kind capability statements in the system prompt (they are per-session-stable), which Reasonix's single-role design doesn't need — justified by the multi-kind tool surfaces.

## 2. Decisions

- **R-D1 — Continuation mechanics: replay stored bytes, append the new phase as a user message.** A continuation dispatch loads the predecessor's persisted transcript and replays it **verbatim** (stored `contract.Message` structs; raw `ReasoningDetails` preserved; complete tool pairings enforced at save time), then appends one new user message carrying the successor's handoff (phase assignment, carry-forward notes, staleness re-read directives). The system message, tool array, model, and pin are the predecessor's — byte-identity from token 0. The successor's *role* (e.g., review-after-implement) is expressed entirely in the appended user message. Rationale: R-F5–R-F9 prove replay determinism is already tested per provider; anything else (re-marshaling state, new system prompt) breaks the prefix. Alternatives rejected: digest-only seeding (0% predecessor cache reuse — abandons P1), re-rendered transcripts (byte drift), new-pin-per-chain (loses gateway model pin + OR stickiness, R-F11).
- **R-D2 — Cross-kind continuation without changing the tool array: harness-side capability masking.** Review-after-implement continues the implementer's stream — same system message ("general" identity), same full tool array on the wire — but the harness's `dispatchScope` for the continuation refuses mutating tools with a bounded denial ("this continuation is review-only..."). The provider-visible schema never changes (MiniMax tool-list-first prefix survives, R-F20); enforcement lives where it always has (the shared gate chain, R-F18). This resolves the critic's hard-risk #1 without renegotiating the 011 pin taxonomy. Alternative rejected: switching to the review kind's system prompt/toolset — guaranteed full cache wipe, the exact thing the link exists to avoid.
- **R-D3 — Transcript persistence: per-run sidecar, verbatim, additive.** New `~/.muhiya/sessions/<id>/agents/<runId>.json` storing the run's `[]contract.Message`, model ID, pin, kind, final usage (prompt+completion tokens), terminal shape, and the read/write-set (R-D5). The session-sidecar allowlist regex extends additively (`agents/` prefix). Stored **unredacted** — byte-identity is mandatory for replay, and the precedent is already set: history.json/knowledge.json are written unredacted via `WriteJSON` today (critic-verified); the store inherits the same OS-level protection as existing session data, and this is recorded as a documented, owner-visible property. Bounded: records pruned with their session; a per-session cap (count + bytes) evicts oldest-completed first.
- **R-D4 — Linkable terminal shapes.** New per-run terminal-shape marker: `clean-done` / `wrapup-done` (turn-exhausted but reported during wrap-up — today indistinguishable from done, R-F16) / `partial-ceiling` / `failed` / `cancelled`. **Stream continuation requires `clean-done`.** `wrapup-done` and `partial-ceiling` transcripts end with injected budget messages and unexecuted-tool results that would teach the successor wrong behavior — they link via the digest fallback. `failed`/`cancelled` never link (a cancelled run may end mid-tool-call, R-F8). Recorded in every link decision per FR-003.
- **R-D5 — Read-set capture with end-of-run fingerprints (solves self-edit staleness).** Subagent dispatch gains a per-run read/write recorder (a scope flag beside dedupe/trackStats — same chokepoint, no new code path): every successful read records path + line range; every mutation records path. At run **completion**, the harness re-stats every touched path once and stores the *final* mtime+size fingerprints in the Context Record. Staleness for a prospective continuation = current stat vs **end-of-run** fingerprint — the predecessor's own edits are therefore never "stale" (critic hard-risk #2 dissolved: the implement→implement chain compares against post-edit state). Majority threshold (Clarification Q5): continuation declined when >50% of the touched set changed since run end. mtime+size is accepted as the fingerprint (the repo's only existing primitive; content hashing rejected as scope creep under Constitution VIII — the residual same-size-same-mtime blind spot is documented and mitigated by the gate's re-read directives for *any* changed-set members). Path normalization: the inspection ledger's workspace-relative lowercased key is the single normalization for the new store.
- **R-D6 — Fix R-F3: move the per-run handoff out of the system message for ALL subagent dispatches.** The subagent system message becomes per-kind-per-session **stable** ("You are the <kind>... " + spec.System + workspace + capability statement); the HANDOFF CONTRACT moves to the first user message, joined with the task text. Every fresh dispatch of a kind then reuses the kind's cached system+tools prefix (DeepSeek from token 0; MiniMax tool-list+system per R-F20). This is a one-time reviewed cache epoch (handoff_test + wiring goldens regenerate once) and the single biggest steady-state win beyond linking itself. Constitution II statement: no content is removed — the handoff moves from system to user position within the same request.
- **R-D7 — Plan access: a `read_plan` registry tool + phase-enriched handoffs.** FR-007 is served two ways: (a) implement/review handoffs embed the phase's step titles **plus the plan Note's Verification/Risks digest** (bounded), closing the "step titles only" gap (R-F14); (b) a new read-only registry tool `read_plan` (returns the rendered plan, optionally a named phase section) is added to all four kind allowlists, served from the session store by the harness — no outside-workspace filesystem prompt (which the critic showed would fire otherwise). The tool-array change is part of the same one-time cache epoch as R-D6. Alternative rejected: in-workspace plan copy (pollutes the user's repo; write-visibility issues).
- **R-D8 — Read gate scope (resolves critic hard-risk #3).** The phase-scoped gate denies main-model `read_file` full-content reads AND shell-read equivalents (reusing the terminal-read regex, R-F18) **only** when: orchestrated ∧ depth==full ∧ state==implementing ∧ phase not degraded ∧ no failed dispatch this phase. Exempt: light-depth entirely (implements in main conversation by design), validating state (its own instruction says "review the changed files"), degraded/recovery paths (their advance-notice texts promise main-model reads), `read_plan`, and post-failure diagnosis (first subagent failure in the phase lifts the gate for the phase's remainder, recorded). `grep`/`search_text`/`glob`/`list_files`/`git_*` stay ungated (discovery ≠ implementation reading; gating them cripples orchestration and contradicts the denylist philosophy precedent). Gate-policy compliance: registered denial text (instructions registry, Sidecar cache class), telemetered (`phase-read-block`), Failed:true, **bounded ≤2 denials then accept-with-recorded-degradation (`read-gate-waived`)** — satisfying clause (c) and the fault-injection invariant. `canOverwrite` deadlock impossible: the gate never applies to subagents, and a waived gate restores main-model reads.
- **R-D9 — Follow-up relatedness predicate (explicit, recorded).** Candidate: the session's most recent chain whose task lifecycle is terminal. Related iff: (a) ≥1 ≥4-char term of the new task matches a path in the candidate's touched set or a plan step title (the existing BriefingForScope extraction, deterministic), (b) same model+pin still configured, (c) staleness ≤ threshold (R-D5), (d) terminal shape linkable (R-D4). No match → digest fallback (cheap, honest). The paraphrase weakness is accepted and recorded — a missed link costs one warm-prefix opportunity, never correctness.
- **R-D10 — Window-overflow predicate.** Decline continuation when `predecessorFinalPromptTokens + handoffEstimate + responseHeadroom(20%) > ModelProfile window` (DefaultContextWindow, ContextWindowLimit — both known client-side; the run's final prompt size is stored in the Context Record from provider-reported usage). Data verified to exist (critic gap closed).
- **R-D11 — Fix the planning-briefing gap (R-F15) in this feature.** The research→planning mid-Run transition appends the findings briefing to the research status line (bounded, once), so the planner has the findings the role separation assumes. Without this the read gate's premise ("main model orchestrates from reports, not file reads") is false at the planning phase — this is a correctness precondition, not scope creep.
- **R-D12 — Measure-first provider gates (resolves critic hard-risk #4).** Three cheap live probes precede any SC commitment and any behavior-change merge: **P1** DeepSeek continuation probe (tiny subagent → continue → compare `prompt_cache_hit_tokens` vs predecessor's last `prompt_tokens`; settles the end-of-output boundary, R-F22); **P2** MiniMax production-routing truth (operator query of the production providers/models tables: direct vs OpenRouter; then the same continuation probe on the real path — decides whether SC-005's 70% MiniMax target is achievable or must be re-scoped to direct-MiniMax); **P3** effort-flip probe on DeepSeek (does a `reasoning_effort` change alone cold the prefix — decides whether continuations must pin effort to the predecessor's). Live probes cost real money → **owner permission required before running** (standing constraint). SC-001/SC-005 numbers are conditional on probe outcomes; the honest "linked but cold" display path (US3-AS2) ships regardless.
- **R-D13 — Metrics & visibility schema.** `TaskStats` gains `Links []LinkOutcome` (per dispatch: predecessor, form used, decision reason, first-request paired cache share, files inherited vs re-read); bench JSON gains a `links` array and true per-pin spend attribution (retiring the T032 placeholder). Continuations reuse the predecessor's (model, pin) pairing so `PerPairingRates` needs no cold-write special-casing (R-F12). All figures provider-reported or labeled unavailable.
- **R-D14 — Doc truth.** Code is authoritative on the pin taxonomy (feature 011 D4); docs/prompt-caching.md's `:aux` classification pin and flat `:sub` pins are corrected in this feature's doc sync (Constitution: Development Workflow gate).

## 3. Open items carried into design (all bounded, none blocking)

1. **P2 outcome fork**: if production MiniMax is direct (as migrations suggest), the spec's "MiniMax through OpenRouter" phrasing adjusts to "MiniMax (as routed by the gateway)" — the design is identical either way (the gateway owns routing; the client's job is pin stability + byte-identical replay).
2. **DeepSeek end-of-output boundary (P1)** decides only the *predicted* size of the first-continuation miss (final assistant turn + handoff vs handoff alone) — not the architecture.
3. **Turn-exhaustion relabeling (R-D4's `wrapup-done`)** doubles as a fix for the verified "silent group completion" hazard (R-F16); validation remains the backstop either way.
4. tasks.md (the plan.md write-only twin) is kept as-is — external-consumer contract status unknown, removal is out of scope (Constitution VIII).
