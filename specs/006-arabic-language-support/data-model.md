# Data Model: Arabic Language Support

This feature is presentation-centric; it introduces **no new persisted schema** and no new session/state files. The "data model" is the in-memory text model that separates the logical source of truth from its terminal presentation, plus the already-existing RTL settings. Everything below is derived from the spec's Key Concepts (FR-013/FR-014/FR-009) and the Constitution's dynamic-vs-cached separation.

## Core value types

### LogicalText (source of truth)

- **What it is**: A string of standard Unicode code points in logical (reading/keystroke) order — e.g. `افتح main.go`.
- **Where it lives**: transcript item content, the composer's `Value()`, session history, project context (`MUHIYA.md`/`MEMORY.md`), and the clipboard.
- **Invariants**:
  - It is the ONLY form ever sent to the model, persisted, or copied.
  - It is normalized to Unicode NFC before being sent to the model and before hashing/prefix use, so equivalent sequences don't drift (decision in research.md). NFC never changes displayed meaning.
  - It is never mutated by any display transform.

### VisualText (display-only, ephemeral)

- **What it is**: A per-display-line transformation of `LogicalText`: Arabic base letters replaced by contextual presentation forms (isolated/initial/medial/final) and RTL runs reversed, so a BiDi-agnostic terminal shows correct joined, right-to-left glyphs.
- **Where it lives**: only inside a single `View()` frame (the rendered viewport string, the composer's rendered lines). Never stored, sent, or copied.
- **Invariants**:
  - Produced only when the active RTL mode calls for app-side shaping (`visual`, or `auto` on a non-BiDi terminal) AND the line actually contains RTL characters (`IsRTL`).
  - Pure-LTR lines pass through unchanged (byte-identical to today).

### DirectionalRun

- **What it is**: A maximal span of one display line with a single resolved direction. Fields: `text`, `direction` (LTR|RTL), `logicalStart`, `logicalEnd` (rune indices into the line's logical text).
- **Produced by**: the bidirectional algorithm (`golang.org/x/text/unicode/bidi` `Paragraph.Order()`), with base direction resolved per line (first-strong, or forced by paragraph override for RTL-dominant lines).
- **Use**: mixed content — Latin words, numbers, `code`, paths, URLs form LTR runs that stay intact and correctly positioned inside surrounding Arabic RTL runs (FR-010).

### DisplayLine

- **What it is**: The rendered representation of one logical line. Fields:
  - `visual` (VisualText for the screen),
  - `logical` (the LogicalText this line came from),
  - `cellMap` (each visual glyph-cell → the logical rune index/span it came from, and the inverse), used to copy logical text from a visual selection and to place the composer caret,
  - `align` (left|right) resolved from the line's dominant direction and the `RTL.Align` setting.
- **Invariants**:
  - `cellMap` is generated by the SAME pass that produces `visual`, so the two never disagree (single source of truth). Shaping/BiDi is a pure function `logical → (visual cells + cellMap)` that never mutates the logical buffer.
  - A ligature cell (e.g. lam-alef ﻻ) maps back to **multiple** logical indices; the map is glyph-cell→logical-span, not strictly 1:1.
  - RTL runs are reversed **per run and grapheme-aware** (base+combining marks stay together) — never a whole-line `bidi.ReverseString` (which mis-handles combining marks; see research R8/E3).
  - Widths account for combining marks as zero-width and CJK/emoji as wide (grapheme-aware width).
  - Copy/selection is anchored in **logical** offsets (resolved via `cellMap`); the clipboard payload is a slice of `logical`, never reconstructed from on-screen glyphs (the visual transform is provably non-invertible — research R3).

### RTLSettings (persisted — already exists)

- **Fields** (in `settings.json`, `contract.Settings.RTL`):
  - `mode`: one of `auto` | `visual` | `native` | `off`.
  - `align`: one of `auto` | `right` | `left`.
- **Validation** (existing, unchanged): membership-checked on load/set (`internal/state/config.go`).
- **Semantics**:
  - `auto` — the default: app-side `visual` shaping with terminal BiDi suppressed (see negotiation below); RTL handling engages only on lines that contain RTL characters.
  - `visual` — always app-side shape + reorder.
  - `native` — never reorder app-side; emit logical text and let the terminal's BiDi engine render it (prevents double-reversal).
  - `off` — no RTL handling at all (escape hatch).
  - `align: auto` — right-align lines whose dominant direction is RTL, left-align others. `right`/`left` force it.
- **New behavior**: `align` becomes actually applied (today it is stored/validated but unused).

### Terminal BiDi negotiation (no runtime capability entity)

- **What it is**: Not a detected value — a startup **negotiation**. There is no reliable capability handshake, so `auto`/`visual` emit BDSM-explicit `CSI 8 l` (restore `CSI 8 h` on exit) to suppress terminal-side BiDi and prevent double-reversal on capable terminals; `native` emits BDSM-implicit `CSI 8 h` and skips app-side reordering.
- **Lifecycle**: emitted once at startup with the alt-screen setup; restored on teardown.
- **Invariant**: purely a display-stream negotiation; the sequences are ignored by BiDi-agnostic terminals and MUST NOT enter the model request or the stable prefix.

## Relationships & flow

```text
LogicalText (item / composer / history / memory)
     │  wrap to width (logical)               ← wrap FIRST (research decision)
     ▼
Logical line ──► RTL display pass ──► DisplayLine{ visual, logical, colMap, align }
     │                                   │
     │                                   ├─► screen (viewport / composer render)
     │                                   └─► colMap ──► selection copy → LogicalText (clipboard)
     ▼
LogicalText (NFC) ──► user message ──► model     ← never VisualText
```

## Validation & rules (requirement traceability)

| Rule | Source |
|------|--------|
| Only LogicalText is sent/stored/copied; VisualText is ephemeral | FR-009, FR-013, FR-014, FR-015 |
| Pure-LTR lines are byte-identical to today | FR-011, SC-008 |
| Combining marks are zero-width for column/alignment math | FR-006 |
| LTR runs (numbers/code/paths/URLs) stay intact & positioned in RTL context | FR-010, FR-012 |
| Right-align dominant-RTL blocks per `RTL.Align` | FR-003 |
| `native` mode never reorders app-side (no double-reversal) | FR-018, SC-008 |
| RTL settings change applies live, no restart | FR-020 |
| RTL never enters the stable prompt prefix | FR-016, SC-006 |

## State transitions

- **Setting change** (`mode`/`align` via `config` or a future `/rtl`): next render reflects it; no restart; no effect on an in-flight request (FR-020).
- **BiDi negotiation**: emitted once at startup (`CSI 8 l` for `auto`/`visual`, `CSI 8 h` for `native`); restored on exit.
- **No persistent state machine** otherwise — rendering is a pure function of (logical text, width, mode, align, capability).
