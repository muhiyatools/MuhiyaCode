# Contract: Context Compiler and Task Epochs

## 1. Request layout

The logical order is stable and provider-adapted without changing meaning:

```text
1. core tool schemas                         session-stable
2. universal system prompt                  session-stable
3. project root context/index               prefix-epoch-stable
4. selected prior task capsules             task-epoch-stable
5. current task goal + explicit user text   task-epoch/current tail
6. current execution checkpoint             replaceable at deliberate checkpoint
7. active exact evidence/observation cards  append-only within checkpoint interval
8. newest user steering/control             request tail
```

Provider wire order may place tools before system because the API does, but the manifest keeps one canonical logical order and records final wire hashes.

## 2. Protected content

Never remove automatically:

- system safety and permission rules
- explicit current user requirements
- unresolved user decisions
- exact active patch/change target required for the next mutation
- failing test identifiers/locations required for repair
- provider-required assistant reasoning/tool-use blocks inside an active chain
- latest file fingerprints and external-change warnings
- unsettled task checkpoint

## 3. Lossless reduction ladder

Apply in order:

1. Do not include content that was never selected.
2. Deduplicate identical observations by content hash.
3. Replace raw tool output with its initially generated bounded observation card.
4. Fetch exact ranges rather than whole artifacts.
5. Drop superseded observations whose source fingerprints changed, retaining a stale marker.
6. At task boundary, start a new epoch with relevant capsules.
7. At milestone boundary, replace completed working history with a task checkpoint if break-even passes.
8. Only then run query-aware model summarization for genuinely semantic conversation content.

Steps 1-6 require no LLM call.

## 4. Relatedness classifier

The classifier returns `continue`, `new_epoch`, or `uncertain` with a score and reason codes.

Required signals:

```text
explicit continuation/correction language
named path overlap
symbol overlap
issue/task/checklist identity overlap
current changed/read file overlap
goal lexical BM25 overlap
time/turn recency
current epoch settled state
new top-level path/domain evidence
```

Short replies inherit the active epoch. `new_epoch` is forbidden while the current epoch is unsettled unless the user explicitly replaces/cancels the task.

## 5. Capsule retrieval

Inputs: current goal, named paths/symbols, workspace fingerprint, token budget, max items.

Pipeline:

1. Filter wrong workspace/security owner.
2. Filter corrupt capsules.
3. Validate referenced file fingerprints; mark historical or exclude stale operational facts.
4. Score lexical/path/symbol/dependency/recency/user pin.
5. Select via MMR until token budget or max items.
6. Put highest-value capsule near the tail of the capsule block; preserve deterministic tie ordering by ID.
7. Record selection and exclusions in manifest.

No capsule is injected because it is merely recent.

## 6. Milestone checkpoint

A checkpoint has:

```text
GOAL
CURRENT PHASE
COMPLETED CHANGES (runtime file ledger)
VERIFICATION (runtime check ledger)
ACTIVE FAILURES
DECISIONS/CONSTRAINTS
NEXT REQUIRED ACTION
EVIDENCE HANDLES
```

Exact paths, hashes, statuses, numbers, and handles are generated by runtime. Narrative clauses may be model-produced only if tagged as narrative and bounded.

## 7. Break-even decision

Use the formula in `research.md` with provider weights. Required gates:

- predicted savings margin >= configured minimum (default experiment: 20%)
- dependency confidence >= threshold
- checkpoint persisted
- no unresolved provider protocol chain that requires full replay
- hysteresis cooldown satisfied

Observe mode records the decision without changing context.

## 8. Prefix and invalidation

Each request stores:

- core-tools hash
- system hash
- project-root hash
- task-epoch ID
- context revision
- settled-message prefix hash

Events:

| Event | Valid effect |
|---|---|
| core tool change | new stable-prefix epoch; cold start declared |
| system/project root change | new prefix revision; declared |
| new task epoch | messages replaced deliberately; core prefix unchanged |
| milestone checkpoint | task history replacement; revision increments |
| artifact fetch | tail append only |
| user steering | tail append only |

No mid-history mutation is allowed without an event committed first or atomically with it.

## 9. Failure behavior

- Capsule/checkpoint persistence failure: keep old context; do not reset.
- Retrieval index failure: scan bounded canonical capsule metadata; if still unavailable, retain current context.
- Artifact missing: emit honest missing-artifact observation and reacquire source if safe.
- Relatedness uncertain: continue current epoch or ask one blocking question.
- Provider cache fields unavailable: make quality-safe context decisions; cost optimization remains observe-only.

## 10. Tests

- Direct follow-up, correction, continuation token, unrelated task, two-topic alternation.
- External file mutation invalidates operational capsule facts.
- Exact prior decision retrieval from 1,000 capsules under token budget.
- MMR prevents five near-duplicate capsules from crowding one required different fact.
- Context reset cannot occur before durable checkpoint.
- Prefix hash stable across tail appends and artifact fetches.
- Crash at every checkpoint transaction boundary recovers old or new state, never a mixture.
